# 用户模块类型定义文档

> 本文档系统性整理了用户模块的 TypeScript 类型定义，识别冗余并提出统一方案。

---

## 一、类型架构概览

### 1.1 类型定义分布

| 文件位置                                                | 用途                      | 说明                         |
| ------------------------------------------------------- | ------------------------- | ---------------------------- |
| `packages/common/src/user/user.interface.ts`            | **前端共享类型**          | 前端 API 调用类型定义        |
| `app/q-server/src/modules/user/schemas/user.schemas.ts` | **Zod Schema + 类型推导** | 后端请求校验，类型自动推导   |
| `app/q-server/src/utils/response.ts`                    | **后端响应类型**          | 运行时使用的响应结构和错误码 |
| `app/q-server/src/modules/user/auth.service.ts`         | **服务层类型**            | 服务内部返回类型定义         |

### 1.2 当前状态：存在冗余但不兼容

由于命名风格和类型结构差异，当前无法直接合并类型定义：

```
packages/common/user.interface.ts (前端使用)
    ├── BizCode: PascalCase (EmailExists, VerifyCodeInvalid)
    ├── ApiResponse.data: T (非 null)
    └── LoginResponse.tokenType: "Bearer" (字面量类型)

app/q-server/utils/response.ts (后端使用)
    ├── BizCode: SCREAMING_SNAKE_CASE (EMAIL_EXISTS, VERIFY_CODE_INVALID)
    ├── ApiResponse.data: T | null
    └── LoginResult.tokenType: string
```

## 三、共享类型定义（前端）

> 以下类型定义于 `packages/common/src/user/user.interface.ts`，供前端使用

### 3.1 通用响应结构

#### ApiResponse<T>

```typescript
interface ApiResponse<T = null> {
  data: T; // 业务数据，失败时为 null
  code: number; // 业务状态码，0 表示成功
  msg: string; // 提示信息
}
```

**使用示例：**

```typescript
// 成功响应
const res: ApiResponse<LoginResponse> = {
  data: { token: "...", user: {...} },
  code: 0,
  msg: "登录成功"
};

// 失败响应
const res: ApiResponse<null> = {
  data: null,
  code: 1001,
  msg: "邮箱已被注册"
};
```

### 3.6 API 类型映射

```typescript
interface AuthApi {
  status: { request: void; response: SystemStatusResponse };
  login: { request: LoginRequest; response: LoginResponse };
  sendCode: { request: SendCodeRequest; response: SendCodeResponse };
  register: { request: InitRegisterRequest; response: InitRegisterResponse };
  verifyRegister: { request: VerifyRegisterRequest; response: VerifyRegisterResponse };
  refresh: { request: RefreshTokenRequest; response: LoginResponse };
  logout: { request: void; response: null };
}

interface AdminApi {
  createUser: { request: CreateUserRequest; response: CreateUserResponse };
  listUsers: { request: UserListQuery; response: UserListResponse };
  updateUser: { request: UpdateUserRequest; response: UpdateUserResponse };
  deleteUser: { request: void; response: DeleteUserResponse };
  getConfig: { request: void; response: SystemConfigResponse };
  updateSmtp: { request: UpdateSmtpConfigRequest; response: UpdateSmtpConfigResponse };
}
```

**使用示例：**

```typescript
import type { AuthApi, ApiResponse, BizCode } from "@common/user/user.interface";

// 前端 API 调用类型约束
async function login(body: AuthApi["login"]["request"]): Promise<ApiResponse<AuthApi["login"]["response"]>> {
  return fetch("/api/auth/login", { method: "POST", body: JSON.stringify(body) }).then(res => res.json());
}

// 错误码判断（使用前端命名风格）
if (res.code === BizCode.EmailExists) {
  // 处理邮箱已注册错误
}
```

## 五、类型不一致问题分析

### 5.1 问题清单

| 问题                      | 影响                                       | 严重程度 |
| ------------------------- | ------------------------------------------ | -------- |
| BizCode 命名风格不一致    | 前后端错误码判断代码不同                   | 中       |
| ApiResponse.data 类型差异 | 前端类型定义 `T`，后端实际返回 `T \| null` | 低       |
| tokenType 类型差异        | 前端 `"Bearer"` 字面量，后端 `string`      | 低       |
| 类型定义重复              | 维护成本增加，可能出现不一致               | 中       |

### 5.2 根因分析

1. **历史演进**：`packages/common` 为后续新增的共享包，类型定义与后端原有定义风格不同
2. **命名规范差异**：前端遵循 TypeScript 常见风格（PascalCase），后端遵循传统常量风格（SCREAMING_SNAKE_CASE）
3. **类型精确度差异**：前端追求类型精确（字面量类型），后端追求灵活性（宽泛类型）

## 六、统一方案建议

### 6.1 短期方案：保持现状，文档记录

当前状态：前后端各自维护类型定义，语义一致但命名/结构有差异。

**优点：**

- 无需修改现有代码，风险低
- 前后端独立演进

**缺点：**

- 类型冗余，维护成本增加
- 前后端类型名称不同，开发者需注意

### 6.2 中期方案：统一命名风格

**步骤：**

1. **统一 BizCode 命名风格**
   - 选择一种风格（建议 PascalCase，符合 TypeScript 常见规范）
   - 修改后端 `response.ts` 中的 BizCode 枚举
   - 更新所有使用 BizCode 的代码

2. **统一 ApiResponse 结构**
   - 前端 `data: T` 改为 `data: T | null`，与后端一致
   - 或后端 `data: T | null` 保持不变，前端类型定义需明确标注

3. **统一 tokenType 类型**
   - 后端 `LoginResult.tokenType` 改为 `"Bearer"` 字面量类型

### 6.3 长期方案：共享类型包

**步骤：**

1. 在 `packages/common` 中定义所有共享类型（单一来源）
2. 后端通过路径别名导入（需配置 tsconfig.json）
3. 前端直接导入使用

**配置示例：**

```json
// app/q-server/tsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@common/*": ["../../packages/common/src/*"]
    }
  }
}
```

**导入示例：**

```typescript
// 后端
import { BizCode, ApiResponse } from "@common/user/user.interface.js";

// 前端
import { BizCode, ApiResponse } from "@common/user/user.interface";
```

## 七、注意事项

1. **BigInt 序列化**：数据库 `id` 字段为 `BigInt`，后端序列化为字符串，前端类型定义为 `string`
2. **命名风格注意**：前端使用 `BizCode.EmailExists`，后端使用 `BizCode.EMAIL_EXISTS`
3. **类型来源**：前端优先使用 `packages/common` 类型，后端使用本地定义
4. **Zod 类型**：后端校验使用 Zod Schema 推导类型，与共享类型语义一致

---

## 八、后续优化建议

1. **统一 BizCode 命名风格**：建议采用 PascalCase，一次性修改后端代码
2. **统一 ApiResponse.data 类型**：改为 `T | null`，与实际返回值一致
3. **添加类型转换函数**：提供 `toApiResponse()` 函数，确保类型安全
4. **前端 API 封装**：基于 `AuthApi` / `AdminApi` 类型映射封装前端请求函数
5. **类型测试**：添加类型测试，确保前后端类型一致性
