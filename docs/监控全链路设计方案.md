## 一、现状分析与设计目标

### 1.1 现有基础设施盘点

| 组件 | 当前用途 | 可复用性 |
|------|---------|:---:|
| **RabbitMQ** | 日志传输（Pino → log-consumer → MongoDB） | ✅ 直接复用，新增 tracking-exchange |
| **MongoDB** | 系统日志存储（questionnaire_logs） | ⚠️ 可过渡使用，长期应由 ClickHouse 替代 |
| **Redis** | 限流计数器、Token 黑名单 | ✅ 可复用做实时计数 |
| **PostgreSQL (Prisma)** | 业务数据 + audit_logs | ⚠️ 不适合时序埋点数据 |
| **pnpm monorepo** | 共享包管理（packages/*） | ✅ 新 SDK 放入 packages/tracking-sdk/ |
| **Fastify hooks** | onResponse / onRequest 生命周期 | ✅ 接口监控可直接挂载 |
| **Pino logger** | 结构化日志 + 自动脱敏 | ✅ 复用脱敏逻辑 |
| **SSE Client** | AI 流式传输 | ✅ AI 耗时埋点可直接在 SSE 回调中上报 |
| **Vue 3 生态** | router / pinia / axios | ✅ SDK 以 Vue Plugin 形态集成 |

### 1.2 当前监控盲区

| 盲区 | 影响 |
|------|------|
| 前端 JS 运行时错误完全不可见 | 用户遇到白屏/功能异常，开发团队不知道 |
| 无页面加载性能数据 | 不知道编辑器/问卷填写页的真实加载速度 |
| 无用户行为追踪 | 无法分析功能使用率、用户路径、弃填原因 |
| AI 生成无端到端可观测性 | SSE 流中断原因不明，生成质量无法量化 |
| 无业务漏斗分析 | 不知道"创建问卷 → 发布 → 收集答卷"各环节转化 |
| 接口调用无客户端视角数据 | 仅服务端日志，DNS/网络延迟不可见 |

### 1.3 设计目标

1. **全端覆盖**：三个前端应用 + 两个后端服务的可观测性统一
2. **对业务零侵入**：埋点失败不影响任何业务流程
3. **存储成本可控**：利用 ClickHouse 列式压缩 + TTL 自动过期
4. **实时 + 离线双模**：关键错误实时告警，分析报表 T+1 可查
5. **自主可控**：不依赖第三方 SaaS，数据完全自持有

## 三、数据采集策略

### 3.1 埋点数据分类

埋点事件按性质分为四大类，决定采集方式、上报优先级和存储策略：

#### A 类：错误事件（Error Events）

| 特征 | 说明 |
|------|------|
| **优先级** | 最高，实时上报 |
| **体积** | 极小（< 1KB/条） |
| **频率** | 低频（正常 < 20 条/分钟） |
| **上报策略** | 立即发送，不缓冲，失败时 localStorage 持久化重试 |

| 事件名 | 采集位置 | 属性 |
|--------|---------|------|
| `js_error` | `window.onerror` + `unhandledrejection` | error_message, error_stack, error_type, component_name, page_url, user_agent |
| `vue_error` | `app.config.errorHandler` | 同上 + component_tree, props_keys |
| `api_error` | axios 响应拦截器（status >= 500 或网络错误） | api_path, http_status, response_body(截断200字), duration_ms |
| `sse_error` | SSE Client onError 回调 | stream_type(ai_generate / ai_polish), error_reason, received_bytes |
| `resource_error` | `window.addEventListener('error')` 捕获资源加载失败 | resource_url, resource_type(script/style/image), page_url |

#### B 类：性能事件（Performance Events）

| 特征 | 说明 |
|------|------|
| **优先级** | 中，缓冲批量上报 |
| **体积** | 小（< 500B/条） |
| **频率** | 每页面路由一次 |
| **上报策略** | 内存缓冲，页面空闲时批量发送 |

| 事件名 | 采集位置 | 属性 |
|--------|---------|------|
| `page_perf` | Web Vitals API (FCP/LCP/TTI/CLS/INP) | fcp_ms, lcp_ms, tti_ms, cls, inp_ms, page_url, connection_type |
| `api_perf` | axios 拦截器（所有请求） | api_path, duration_ms, http_status, response_size_bytes |
| `resource_perf` | PerformanceObserver (resource) | 仅采集 > 500ms 的慢资源：resource_url, duration_ms, resource_type |
| `editor_perf` | 编辑器关键操作手动埋点 | action(undo/redo/add_component/save), duration_ms, component_count |

#### C 类：行为事件（Behavior Events）

| 特征 | 说明 |
|------|------|
| **优先级** | 低，缓冲批量上报 |
| **体积** | 中（< 2KB/条） |
| **频率** | 中频（每日总量取决于用户量） |
| **上报策略** | 内存缓冲，50条/次或 10s 间隔触发冲刷 |

| 事件名 | 触发场景 | 核心属性 |
|--------|---------|---------|
| `page_view` | Vue Router afterEach 自动采集 | page_url, referrer, page_title, is_first_visit |
| `survey_view` | C 端打开问卷链接 | survey_id, source_channel, is_public |
| `survey_submit_start` | 点提交按钮 | survey_id, answered_count, total_count, elapsed_s |
| `survey_submit_success` | 提交成功 | survey_id, answered_count, elapsed_s |
| `survey_submit_fail` | 提交失败 | survey_id, fail_reason, error_message |
| `survey_abandon` | 填卷中途关闭页面 (sendBeacon) | survey_id, answered_count, total_count, stay_s |
| `editor_create_survey` | 新建问卷 | source(scratch/template/ai) |
| `editor_add_component` | 添加题目 | component_type, add_method(drag/click/ai) |
| `editor_publish_survey` | 发布问卷 | survey_id, component_count, has_ai_generated |
| `editor_use_ai_generate` | 使用 AI 生成 | prompt_length, generated_count, elapsed_ms |
| `editor_use_ai_polish` | 使用 AI 润色 | component_count, polish_aspects[], elapsed_ms |
| `admin_approve_review` | 审核通过 | review_id, review_type(survey/template) |
| `admin_ban_user` | 封禁用户 | target_user_id, duration_minutes |
| `user_login` | 登录成功 | login_method(password/code) |
| `user_logout` | 登出 | session_duration_s |
| `component_click` | 点击非导航类交互元素（采样 10%） | element_id, element_type, page_url |

> **采样说明**：高频事件（如 click、scroll）采用 10% 采样率降低数据量。采样在客户端 SDK 层完成（Math.random < 0.1），不上报到服务端再丢弃。

#### D 类：业务指标事件（Business Metrics）

| 特征 | 说明 |
|------|------|
| **优先级** | 低，批量上报 |
| **体积** | 中 |
| **频率** | 极低频（日均几十条） |
| **上报策略** | 随行为事件批量冲刷 |

| 事件名 | 触发场景 | 属性 |
|--------|---------|------|
| `ai_usage_daily` | AI 用量查询页面访问时异步上报 | prompt_tokens, completion_tokens, estimated_cost |
| `survey_response_aggregated` | 答卷达到阈值（10/50/100条）时 | survey_id, response_count, avg_completion_s |
| `template_apply` | 从模板广场创建问卷 | template_id, template_category, template_rating |

### 3.2 公共字段规范

每条埋点事件必须携带以下公共字段，由 SDK 自动填充：

```text
event_id          UUID v7（时间有序，ClickHouse 排序键）
event_name        事件名，snake_case
app_id            应用标识：q-editor | frontend | main-app | q-server | ai-service
user_id           登录用户 ID（未登录为 null）
anonymous_id      匿名用户 ID（localStorage 持久化，未登录用户的标识）
session_id        会话 ID（sessionStorage，浏览器标签页级别）
device_id         设备 ID（localStorage，跨会话）
timestamp         客户端时间戳（ISO 8601，毫秒精度）
server_timestamp  服务端接收时间戳（tracking-api 补充）
client_env        客户端环境：{ os, browser, browser_version, screen_width, screen_height, network_type, language }
page_url          当前页面完整 URL
page_title        页面标题
sdk_version       tracking-sdk 版本号
```

### 3.3 隐私与脱敏规则（客户端侧）

SDK 在序列化事件属性前自动执行：

| 规则 | 说明 |
|------|------|
| **字段黑名单** | `password`, `token`, `secret`, `apiKey`, `idCard`, `phone`, `email` 等命名字段自动替换为 `[REDACTED]` |
| **正则扫描** | 匹配身份证号（18位）、手机号（11位）、邮箱格式的属性值自动脱敏 |
| **答卷内容隔离** | `survey_submit_*` 事件**不携带任何答卷文本内容**，仅携带计数类属性（answered_count, total_count） |
| **URL 参数清洗** | 自动移除 URL 中的 `token=`, `code=`, `sign=` 等敏感查询参数后再上报 |

## 四、数据传输机制

### 4.1 前端 SDK 缓冲与冲刷策略

```
用户操作 → track(event) 调用
              │
              ├── A 类错误事件 → 立即 sendBeacon()
              │
              └── B/C/D 类事件 → 推入内存队列 (环形缓冲区, 最大 200 条)
                                        │
                          ┌─────────────┼─────────────┐
                          │             │             │
                     达到 50 条     超过 10s      页面隐藏/卸载
                          │        未冲刷           (visibilitychange
                          │        (定时器)          / beforeunload)
                          │             │             │
                          └─────────────┴─────────────┘
                                        │
                               批量 POST /api/v1/track/batch
                                  (JSON 数组, gzip 压缩)
                                        │
                               成功 → 清空缓冲
                               失败 → 保留 + 指数退避重试 (1s→2s→4s→8s→16s)
                               重试仍失败 → 降级写入 localStorage 离线队列
                                           下次初始化或网络恢复时重放
```

### 4.2 上报端点设计

**单条上报（错误事件）**：

```text
POST /api/v1/track
Content-Type: application/json

{
  "event_id": "019a6f80-...",
  "event_name": "js_error",
  "app_id": "q-editor",
  ...公共字段,
  "properties": { ...事件属性 }
}

响应：204 No Content（不返回任何业务数据，减少传输）
```

**批量上报（行为/性能事件）**：

```text
POST /api/v1/track/batch
Content-Type: application/json
Content-Encoding: gzip

{
  "events": [ { ...事件1 }, { ...事件2 }, ... ]
}

响应：204 No Content
```

### 4.3 服务端接收层设计

tracking-api 路由在 q-server 中实现，核心要求：**极速返回，绝不做阻塞操作**。

```text
请求到达 → 轻量校验 → 补充服务端字段 → 投递 RabbitMQ → 返回 204
           (5ms)      (1ms)             (2ms)          (Total < 10ms)

校验规则：
  • event_name 必填，长度 1-64
  • app_id 必填，必须在白名单内
  • timestamp 必填，不能超过未来 5 分钟
  • properties 大小 < 8KB
  • 单条 body < 10KB
  • 批量 body < 500KB
  • 请求频率：单 IP 限制 60 次/秒

服务端补充字段：
  • server_timestamp：精确服务端时间（用于修正客户端时钟偏移）
  • client_ip：经过哈希处理的 IP（SHA256前16位，非明文存储）
  • user_agent_parsed：解析后的 { browser, os, device_type }
  • geo_region：IP 解析出的省份/城市（仅保留到城市粒度）
```

### 4.4 RabbitMQ 配置

```
Exchange: tracking-events
  type: topic
  durable: true

Queue: tracking-errors（错误队列）
  routing_key: error.#
  特性: x-max-length=50000（防止消费者宕机堆积）
  优先级消费

Queue: tracking-analytics（分析队列）
  routing_key: perf.# / behavior.# / metric.#
  特性: x-queue-mode=lazy（减少内存占用，适合大批量）
  批量 ACK: prefetch=200
```

### 4.5 数据一致性保障

| 场景 | 保障机制 |
|------|---------|
| 客户端网络断开 | localStorage 离线队列，最多缓存 500 条，超出则丢弃旧事件 |
| RabbitMQ 宕机 | tracking-api 降级写本地文件（照搬 audit-log 的 fallback 模式） |
| ClickHouse 写入失败 | tracking-consumer 死信队列 + 本地文件兜底，手动回放 |
| 客户端时间不准 | 同时记录 client_timestamp + server_timestamp，分析时以服务端为准 |
| 事件重复 | ClickHouse ReplacingMergeTree + event_id 去重 |

### 5.1 部署模式

| 决策项 | 选择 | 理由 |
|--------|------|------|
| **部署方式** | 单机 → 集群（后续扩展） | 当前数据量预估 < 50万条/日，单机足够（32C/64G/SSD） |
| **存储引擎** | MergeTree 家族 | ClickHouse 核心引擎，支持分区/排序/TTL |
| **分区策略** | 按天分区 `toYYYYMMDD(timestamp)` | 对齐 TTL 清理粒度，查询裁剪高效 |
| **副本** | ReplicatedMergeTree（集群阶段） | 单机阶段可暂不配置，通过每日备份兜底 |

### 5.2 核心表设计

#### 5.2.1 事件明细表（tracking_events）

```sql
-- ============================================================
-- 表名: tracking_events
-- 用途: 所有埋点事件的原始明细存储
-- 引擎: MergeTree（生产可用 ReplicatedMergeTree）
-- 分区: 按天 → 方便 TTL 过期删除
-- 排序键: (app_id, event_name, timestamp) → 按应用+事件类型查询最优
-- 压缩: ZSTD(3) — 平衡压缩率与写入性能
-- ============================================================

CREATE TABLE tracking_events (
    -- 主键/排序列
    event_id        FixedString(16),      -- UUID v7 的 16 字节二进制, 全局去重
    timestamp       DateTime64(3),        -- 毫秒精度, 排序键核心
    date            Date DEFAULT toDate(timestamp),  -- 分区键

    -- 公共字段
    event_name      LowCardinality(String),  -- 事件名（基数低，LowCardinality 压缩率高）
    app_id          LowCardinality(String),  -- 应用标识
    user_id         UInt64 DEFAULT 0,        -- 用户 ID（0=未登录）
    anonymous_id    String,                  -- 匿名用户 ID
    session_id      String,                  -- 会话 ID
    device_id       String,                  -- 设备 ID
    sdk_version     LowCardinality(String),

    -- 时间相关
    client_timestamp    DateTime64(3),   -- 客户端时间（用于偏差分析）
    server_timestamp    DateTime64(3) DEFAULT now64(3),

    -- 客户端环境
    client_os       LowCardinality(String),
    client_browser  LowCardinality(String),
    browser_version LowCardinality(String),
    device_type     LowCardinality(String),  -- desktop / mobile / tablet
    screen_width    UInt16,
    screen_height   UInt16,
    network_type    LowCardinality(String),  -- 4g / 5g / wifi / ethernet

    -- 地理位置（粗粒度）
    geo_region      LowCardinality(String),  -- 省份
    geo_city        LowCardinality(String),  -- 城市

    -- 页面上下文
    page_url        String,
    page_title      String,
    referrer        String DEFAULT '',

    -- 事件属性（半结构化）
    properties      String,     -- JSON 字符串（ClickHouse 有 json 函数族可查询）

    -- 元数据
    client_ip_hash  FixedString(16),    -- SHA256(client_ip) 前16字节
    ingest_batch_id UUID                 -- 记录本事件所属的上报批次

) ENGINE = MergeTree()
PARTITION BY toYYYYMMDD(date)
ORDER BY (app_id, event_name, toStartOfHour(timestamp), timestamp)
TTL date + INTERVAL 90 DAY DELETE      -- 90天自动删除明细
SETTINGS
    index_granularity = 8192,           -- 默认粒度
    min_rows_for_wide_read = 0,         -- 小查询也走宽读
    ttl_only_drop_parts = 1,            -- TTL 只在分区级别生效
    storage_policy = 'default',
    compression = 'ZSTD(3)';

-- 二级索引：加速 user_id 和 session_id 的精确查询
-- ADD INDEX idx_user_id user_id TYPE bloom_filter GRANULARITY 4;
-- ADD INDEX idx_session_id session_id TYPE bloom_filter GRANULARITY 4;
```

#### 5.2.2 错误聚合视图（tracking_errors_hourly_mv）

```sql
-- ============================================================
-- 物化视图: tracking_errors_hourly_mv
-- 用途: 错误事件的每小时聚合, 供告警和趋势图查询
-- 刷新: 物化视图自动增量刷新
-- ============================================================

CREATE MATERIALIZED VIEW tracking_errors_hourly_mv
ENGINE = SummingMergeTree()
PARTITION BY toYYYYMM(date)
ORDER BY (app_id, error_group_key, hour)
TTL date + INTERVAL 365 DAY
AS SELECT
    date,
    toStartOfHour(timestamp) AS hour,
    app_id,
    -- 错误指纹（错误类型 + 前100字符堆栈的 hash，用于去重分组）
    cityHash64(
        concat(
            JSONExtractString(properties, 'error_type'),
            substring(JSONExtractString(properties, 'error_message'), 1, 100)
        )
    ) AS error_group_key,
    JSONExtractString(properties, 'error_type')     AS error_type,
    substring(JSONExtractString(properties, 'error_message'), 1, 200) AS error_message_sample,
    count()                                       AS error_count,
    uniq(user_id)                                 AS affected_users,
    uniq(session_id)                              AS affected_sessions,
    min(timestamp)                                AS first_seen,
    max(timestamp)                                AS last_seen
FROM tracking_events
WHERE event_name IN ('js_error', 'vue_error', 'api_error', 'sse_error', 'resource_error')
GROUP BY date, hour, app_id, error_group_key, error_type, error_message_sample;
```

#### 5.2.3 性能聚合视图（tracking_perf_hourly_mv）

```sql
-- ============================================================
-- 物化视图: tracking_perf_hourly_mv
-- 用途: 页面性能 + API 性能的每小时聚合
-- ============================================================

CREATE MATERIALIZED VIEW tracking_perf_hourly_mv
ENGINE = AggregatingMergeTree()
PARTITION BY toYYYYMM(date)
ORDER BY (app_id, event_name, page_url_hash, hour)
TTL date + INTERVAL 365 DAY
AS SELECT
    date,
    toStartOfHour(timestamp) AS hour,
    app_id,
    event_name,
    cityHash64(page_url) AS page_url_hash,
    any(page_url)         AS page_url_sample,
    count()               AS sample_count,
    avg(JSONExtractFloat(properties, 'fcp_ms'))     AS avg_fcp_ms,
    quantile(0.50)(JSONExtractFloat(properties, 'fcp_ms')) AS p50_fcp_ms,
    quantile(0.95)(JSONExtractFloat(properties, 'fcp_ms')) AS p95_fcp_ms,
    quantile(0.99)(JSONExtractFloat(properties, 'fcp_ms')) AS p99_fcp_ms,
    avg(JSONExtractFloat(properties, 'lcp_ms'))     AS avg_lcp_ms,
    quantile(0.50)(JSONExtractFloat(properties, 'lcp_ms')) AS p50_lcp_ms,
    quantile(0.95)(JSONExtractFloat(properties, 'lcp_ms')) AS p95_lcp_ms,
    quantile(0.99)(JSONExtractFloat(properties, 'lcp_ms')) AS p99_lcp_ms,
    avg(JSONExtractFloat(properties, 'duration_ms')) AS avg_duration_ms,
    quantile(0.95)(JSONExtractFloat(properties, 'duration_ms')) AS p95_duration_ms
FROM tracking_events
WHERE event_name IN ('page_perf', 'api_perf')
GROUP BY date, hour, app_id, event_name, page_url_hash;
```

#### 5.2.4 业务漏斗聚合视图（tracking_funnel_daily_mv）

```sql
-- ============================================================
-- 物化视图: tracking_funnel_daily_mv
-- 用途: 每日关键业务事件计数（漏斗分析数据源）
-- ============================================================

CREATE MATERIALIZED VIEW tracking_funnel_daily_mv
ENGINE = AggregatingMergeTree()
PARTITION BY toYYYYMM(date)
ORDER BY (app_id, event_name, date)
TTL date + INTERVAL 2 YEAR
AS SELECT
    date,
    app_id,
    event_name,
    count()                    AS event_count,
    uniq(user_id)              AS unique_users,
    uniqIf(user_id, user_id != 0) AS unique_logged_in_users,
    uniq(session_id)           AS unique_sessions
FROM tracking_events
WHERE event_name IN (
    'page_view', 'survey_view',
    'editor_create_survey', 'editor_publish_survey',
    'editor_use_ai_generate', 'editor_use_ai_polish',
    'survey_submit_start', 'survey_submit_success', 'survey_abandon',
    'admin_approve_review', 'user_login'
)
GROUP BY date, app_id, event_name;
```

### 5.3 存储容量估算

```text
假设：
  • 日均埋点事件：50 万条（中后期规模）
  • 单条事件压缩前 ~2KB → ZSTD(3) 压缩后 ~0.5KB
  • 日均增量：500,000 × 0.5KB = 250 MB
  • 90 天总量（明细）：250MB × 90 = 22.5 GB
  • 物化视图聚合后数据量约为明细的 1% → ~0.25 GB/天
  • 聚合数据保留 1 年 → ~90 GB

总计（90天滚动明细 + 1年聚合）：
  • 热数据（SSD）：~50 GB
  • 冷备份（OSS/HDFS）：~150 GB

结论：单机 ClickHouse (32GB RAM + 1TB SSD) 可支撑 2-3 年的运营。
```

### 5.4 查询优化策略

| 策略 | 说明 |
|------|------|
| **分区裁剪** | 所有查询必须带 `date` 条件，ClickHouse 自动跳过多余分区 |
| **排序键利用** | 按 `app_id + event_name + 时间` 查询时命中排序键，性能最优 |
| **物化视图优先** | 聚合查询优先查 MV 而非扫明细表 |
| **Prewhere 过滤** | 对 `event_name IN (...)` 条件使用 PREWHERE 自动优化 |
| **查询限制** | 应用层强制 `LIMIT 10000` 和 `max_execution_time=30` |
| **分布式查询** | 集群环境下使用 `ON CLUSTER` 建表，查询走 `distributed` 表 |

## 六、数据处理流程

### 6.1 tracking-consumer 消费进程设计

完全复刻现有 `log-consumer.ts` 的模式：

```text
┌──────────────────────────────────────────────────────────┐
│              tracking-consumer 启动流程                    │
│                                                          │
│  1. 连接 RabbitMQ + ClickHouse（重试 3 次，失败则退出）    │
│  2. 启动主消费循环                                        │
│  3. 注册 SIGTERM/SIGINT 优雅关闭                          │
└──────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────┐
│              消费循环（每轮）                              │
│                                                          │
│  buffer ← []                                             │
│                                                          │
│  WHILE (未关闭) AND (buffer.length < 200):               │
│    从 RabbitMQ 拉取一条消息（1s 超时）                      │
│    IF 消息存在:                                           │
│      JSON.parse → 基础校验 → push 到 buffer               │
│      ACK 该消息                                          │
│                                                          │
│  IF buffer 不为空:                                       │
│    数据清洗:                                              │
│      • 时间戳修正（server_timestamp 补 client_timestamp）   │
│      • 字段类型转换（确保与 CH 表结构匹配）                 │
│      • 空值填充默认值                                     │
│      • event_id 去重（Bloom Filter 内存去重）              │
│                                                          │
│    ClickHouse 批量 INSERT（200 条/批）:                   │
│      INSERT INTO tracking_events FORMAT JSONEachRow      │
│      → 写入失败 → 降级写入本地 JSONL 文件                  │
│      → 写入成功 → 清空 buffer                            │
│                                                          │
│  检查队列堆积:                                            │
│    • > 50000 条 → 发出告警                               │
│    • > 100000 条 → 发出严重告警                           │
└──────────────────────────────────────────────────────────┘
```

### 6.2 数据清洗规则

| 清洗步骤 | 规则 | 异常处理 |
|---------|------|---------|
| **时间戳修正** | `server_timestamp` 为空时用 `now()` 填充；`client_timestamp` 与 `server_timestamp` 偏差 > 1 小时时标记 `client_clock_skew = true` | 不丢弃，标记后继续 |
| **字段截断** | `page_url` > 2048 字符截断；`properties` JSON > 8192 字符截断 | 截断 + 追加 `[TRUNCATED]` |
| **app_id 校验** | 不在白名单内（q-editor / frontend / main-app / q-server / ai-service）→ 改写入 `unknown` | 不丢弃 |
| **event_name 规范化** | 全小写、下划线、去首尾空格 | 非法字符替换为 `_` |
| **user_id 去匿名化** | 如果 `anonymous_id` 匹配到当日已登录的用户，关联补填 `user_id` | 仅当日有效的临时关联 |
| **设备指纹稳定性** | 如果 `device_id` 变化但 `anonymous_id` 相同，保留 device_id 变更记录 | 辅助设备切换检测 |

### 6.3 实时告警处理（同进程内独立协程）

tracking-consumer 同时消费 `tracking-errors` 队列，执行告警判断：

```text
拉取错误事件 → 内存滑动窗口（最近 5 分钟）→ 聚合计数

告警规则匹配：
  • 5 分钟内同 error_group_key 出现 > 50 次 → P2 告警
  • 5 分钟内同 app_id 错误率 > 10% → P1 告警（错误率 = 错误数 / 总请求数）
  • 任何 api_error 中 http_status=502/503/504 出现 > 5 次 → P0 告警（服务不可达）
  • sse_error 单分钟内 > 20 次 → P1 告警（AI 服务异常）

P0: 立即通知（电话/企微@all）
P1: 5 分钟内通知（企微群）
P2: 聚合到每小时报告邮件
```

## 八、告警机制设计

### 8.1 告警分级

| 级别 | 名称 | 响应时间 | 通知方式 | 典型场景 |
|:---:|------|:---:|---------|---------|
| **P0** | 紧急 | 5 分钟内 | 电话 + 企微@all + 短信 | 服务不可用、数据库宕机、RabbitMQ 断连 |
| **P1** | 严重 | 15 分钟内 | 企微群 + 邮件 | 错误率突增、API 大面积超时、AI 服务不可用 |
| **P2** | 关注 | 1 小时内 | 企微单独通知 + 每小时聚合邮件 | 单页面错误率偏高等可延迟处理的问题 |
| **P3** | 信息 | 无需立即响应 | 每日/每周报告 | 性能趋势劣化、存储接近阈值 |

### 8.2 告警规则配置

告警规则应存储在 `system_configs` 表或独立配置文件，支持运行时调整：

```text
告警规则模型:
  {
    rule_id: "err_rate_spike",
    name: "错误率突增",
    type: "threshold",              // threshold | trend | anomaly | heartbeat
    metric: "error_rate",
    dimension: { app_id: "q-editor" },
    condition: {
      window: "5m",                 // 时间窗口
      aggregation: "avg",           // 聚合方式
      operator: ">",                // 比较操作
      threshold: 0.02,              // 阈值
      comparison_window: "1h"       // 对比窗口（趋势检测用）
    },
    level: "P1",
    cooldown: "15m",                // 冷却时间（避免重复告警）
    enabled: true
  }
```

### 8.3 核心告警规则列表

| 规则 ID | 级别 | 条件 | 说明 |
|---------|:---:|------|------|
| `service_down` | P0 | `/health` 连续 3 次失败 | 服务不可达 |
| `db_connection_fail` | P0 | Prisma/Mongoose 连接池耗尽 | 数据库不可用 |
| `mq_connection_fail` | P0 | RabbitMQ 连接断开 | 消息队列不可用 |
| `api_500_spike` | P1 | 5 分钟内 500 错误 > 20 次 | 服务端异常 |
| `js_error_spike` | P1 | 5 分钟内同错误 > 100 次 | 前端大面积崩溃 |
| `api_slowdown` | P1 | P95 耗时 > 1s 持续 5 分钟 | API 性能劣化 |
| `clickhouse_write_fail` | P1 | 连续 3 批写入失败 | 数据管道中断 |
| `mq_queue_backlog` | P2 | 队列堆积 > 50000 | 消费能力不足 |
| `survey_submit_fail_rate` | P1 | 失败率 > 5% 持续 5 分钟 | 答卷提交异常 |
| `ai_service_error_rate` | P1 | SSE 中断率 > 10% 持续 5 分钟 | AI 服务异常 |
| `disk_usage_warning` | P2 | ClickHouse 磁盘 > 80% | 存储即将满 |
| `daily_error_report` | P3 | 每日 10:00 | 前一日错误汇总报告 |

### 8.4 告警通知渠道实现

| 渠道 | 实现方式 | 适用级别 |
|------|---------|:---:|
| **企业微信群机器人** | Webhook POST Markdown 消息 | P0 / P1 / P2 |
| **邮件** | q-server 已有 nodemailer | P1 / P2 / P3 聚合报告 |
| **钉钉机器人** | Webhook POST | 备用渠道 |
| **短信** | 第三方 API（阿里云短信） | P0（仅生产环境） |

### 8.5 告警抑制与升级

```text
告警抑制：
  • 同一 rule_id 在 cooldown 时间内不重复发送
  • 维护窗口内（可配置）的非 P0 告警自动静默
  • 依赖链路抑制：DB 宕机时，不再发"API 超时"告警

告警升级：
  • P2 告警在 1 小时内未被确认 → 自动升级为 P1
  • P1 告警在 30 分钟内未被确认 → 自动升级为 P0
```

## 十、系统扩展性考量

### 10.1 数据量增长应对

| 阶段 | 日均事件量 | 存储方案 | 处理方案 |
|------|:---:|------|------|
| **初期**（当前） | < 10 万 | ClickHouse 单机 | tracking-consumer 单进程 |
| **成长期** | 10-50 万 | ClickHouse 单机（扩容 SSD） | tracking-consumer 单进程（增加 prefetch） |
| **成熟期** | 50-500 万 | ClickHouse 3 节点集群 | tracking-consumer 多进程 + Kafka 替代 RabbitMQ |
| **大规模** | > 500 万 | ClickHouse 分片 + 副本 | Kafka + Flink 流处理 + ClickHouse |

### 10.2 新应用接入

由于 SDK 是 `packages/tracking-sdk/` 共享包，新前端应用接入只需：

```text
1. pnpm add monorepo-tracking-sdk --filter new-app
2. 在 main.ts 中 app.use(TrackingPlugin, { appId: 'new-app', endpoint: '/api/v1/track' })
3. 在 q-server 的 app_id 白名单中添加 'new-app'
4. ClickHouse 无需任何变更（app_id 是 LowCardinality，自动适应新值）
```

### 10.3 新后端服务接入

对于 ai-service（Python FastAPI），可以有两种方式：

| 方式 | 说明 | 优缺点 |
|------|------|--------|
| **HTTP 上报** | ai-service 直接 POST 到 q-server 的 `/api/v1/track` | 简单，复用现有链路；增加一次网络往返 |
| **RabbitMQ 直投** | ai-service 使用 `aio_pika` 直接投递到 `tracking-events` | 更低延迟；需要 Python 侧维护 MQ 连接 |

建议初期使用 HTTP 上报，ai-service 已经有 `httpx` 依赖，开发成本最低。

### 10.4 查询能力扩展

| 阶段 | 查询方式 | 说明 |
|------|---------|------|
| **初期** | q-server 代理 → ClickHouse HTTP | 单表查询，响应 < 1s |
| **中期** | 预计算中间表 + 定时任务 | 复杂漏斗/留存查询从预计算结果读取 |
| **后期** | 引入 OLAP 查询引擎 | 如 Apache Druid 或直接 ClickHouse 集群 |

### 10.5 监控体系的自我监控

监控系统本身也需要监控——"谁监控监控者"：

| 监控项 | 实现方式 | 告警条件 |
|--------|---------|---------|
| tracking-consumer 存活 | 心跳上报到 Redis（TTL 60s） | 超过 60s 无心跳 → P0 |
| 埋点上报成功率 | tracking-api 自身埋点 | 接收/投递成功率 < 99% → P1 |
| ClickHouse merge 延迟 | system.metrics 查询 | merge 落后 > 1 小时 → P2 |
| 数据写入延迟 | 查 tracking_events 最新的 timestamp | 落后 > 15 分钟 → P1 |

## 十一、安全与合规

### 11.1 数据安全分层

| 层级 | 措施 |
|------|------|
| **传输层** | tracking-api 强制 HTTPS；内网 RabbitMQ 走 TLS |
| **存储层** | ClickHouse 磁盘加密（LUKS）；数据库用户最小权限 |
| **应用层** | tracking-api 认证（内部 API Key，与 `q_server_api_key` 共用机制） |
| **数据层** | IP 仅存哈希（不可逆）；答卷内容不上报；敏感字段脱敏 |
| **访问层** | ClickHouse 只读用户给 Grafana 和分析接口；管理后台按角色授权 |

### 11.2 合规要点

| 法规要求 | 实现措施 |
|---------|---------|
| **《个人信息保护法》** | 不采集/存储个人身份信息（PII）明文；`user_id` 是内部数字 ID 不关联真实身份；IP 仅保留哈希 |
| **数据最小必要** | 属性字段白名单制；`properties` JSON 大小限制 8KB；不采集任何答卷文本内容 |
| **数据保留期限** | 明细 90 天自动删除（ClickHouse TTL）；聚合数据 2 年；用户注销后关联数据 30 天内清除 |
| **数据跨境** | 所有数据存储于境内服务器（ClickHouse / RabbitMQ / Redis 均内网部署） |
| **用户告知** | 隐私政策中声明埋点采集范围和用途；提供 opt-out 选项（`window.__TRACKING_OPT_OUT__ = true`） |

### 11.3 Opt-out 机制

```text
SDK 初始化时检查：
  • window.__TRACKING_OPT_OUT__ === true → SDK 加载但不发送任何数据
  • localStorage.getItem('tracking_opt_out') === 'true' → 同上

用户可通过管理后台"隐私设置"页面关闭埋点。
opt-out 状态记录在 localStorage，跨会话生效。
```
