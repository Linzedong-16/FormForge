## 一、需求分析

### 1.1 消息类型体系

```text
┌─────────────────────────────────────────────────────────────────┐
│                      消息类型分类体系                             │
│                                                                  │
│  ┌─────────────────────┐  ┌─────────────────────┐               │
│  │   系统通知类          │  │   用户互动类          │               │
│  │  (system → user)     │  │  (user ↔ user/admin) │               │
│  ├─────────────────────┤  ├─────────────────────┤               │
│  │ • operation_notify   │  │ • user_admin_comm    │               │
│  │   审核结果通知        │  │   用户-管理员私信      │               │
│  │   权限申请结果        │  │                       │               │
│  │ • template_like      │  │ • admin_broadcast     │               │
│  │   模板点赞通知        │  │   管理员群发消息       │               │
│  │ • survey_lifecycle   │  │                       │               │
│  │   问卷发布状态        │  │                       │               │
│  │   问卷过期提醒        │  │                       │               │
│  │   答卷收集里程碑      │  │                       │               │
│  └─────────────────────┘  └─────────────────────┘               │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

| 类型标识 | 中文名称 | 触发场景 | 发送方 | 接收方 |
|---------|---------|---------|:---:|:---:|
| `operation_notify` | 操作通知 | 审核通过/驳回、权限申请结果、用户封禁/解封 | system | 特定用户 |
| `template_like` | 模板互动 | 模板被点赞、模板被应用 | system | 模板作者 |
| `survey_lifecycle` | 问卷生命周期 | 发布成功、审核通过、即将过期（提前7天）、答卷达里程碑(50/100/500) | system | 问卷所有者 |
| `user_admin_comm` | 用户-管理员通信 | 用户向管理员提问、管理员回复 | user/admin | 对方 |
| `admin_broadcast` | 管理员广播 | 系统维护通知、功能更新公告、运营活动 | admin | 全体用户 |

### 1.2 通信权限矩阵

| 发送方 | 接收方 | 是否允许 | 说明 |
|:---:|:---:|:---:|------|
| 普通用户 | 管理员 | ✅ | 双向通信 |
| 管理员 | 普通用户 | ✅ | 双向通信 + 额外拥有广播权限 |
| 普通用户 | 普通用户 | ❌ | 禁止私信 |
| 管理员 | 全体用户 | ✅ | 广播模式 |
| system | 任何用户 | ✅ | 系统自动通知 |

### 1.3 前端交互需求

| 功能 | 位置 | 说明 |
|------|------|------|
| **消息盒子** | q-editor 顶部导航栏 + frontend 管理后台 | 收件箱列表，支持分页、按类型筛选、按已读/未读筛选 |
| **未读红点** | 导航栏消息图标 | 红色圆点 + 未读数字徽标，有新消息时显示 |
| **实时轮询** | 全局 | 每 30 秒拉取未读计数，有新消息时红点亮起 |
| **单条已读** | 消息列表 | 点击消息行即标记已读 |
| **全部已读** | 消息列表顶部 | “全部标记已读”按钮 |
| **消息详情** | 点击消息行展开/弹窗 | 显示完整内容 + 关联资源链接（如跳转到对应问卷） |

### 2.2 事件驱动消息生成

系统通知类消息（operation_notify / template_like / survey_lifecycle）不由用户触发，而是在业务流程中自动生成。采用 **业务钩子（Hook）模式** 实现：

```text
业务操作 → 执行业务逻辑 → 成功
                              │
                              ▼
                    ┌─────────────────────┐
                    │  MessageHookService  │  ← 统一消息钩子服务
                    │  .onReviewResult()   │
                    │  .onTemplateLiked()  │
                    │  .onSurveyPublished()│
                    │  .onSurveyExpiring() │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │  MessageService      │
                    │  .create({           │
                    │    type, sender_id,  │
                    │    recipient_id,     │
                    │    title, content,   │
                    │    resource_type,    │
                    │    resource_id       │
                    │  })                  │
                    └──────────┬──────────┘
                               │
                    ┌──────────▼──────────┐
                    │  写入 DB + 更新缓存   │
                    │  记录审计日志        │
                    └─────────────────────┘
```

## 三、数据库设计

### 3.1 Prisma Schema（在现有 schema.prisma 中新增）

```prisma
// ══════════════════════════════════════════════════════════════
//  消息系统
// ══════════════════════════════════════════════════════════════

enum MessageType {
  operation_notify   // 操作通知（审核结果、权限申请）
  template_like      // 模板互动（点赞、被应用）
  survey_lifecycle   // 问卷生命周期（发布、过期、里程碑）
  user_admin_comm    // 用户-管理员通信
  admin_broadcast    // 管理员广播
}

model Message {
  id                  BigInt      @id @default(autoincrement())
  type                MessageType                        // 消息类型
  title               String      @db.VarChar(200)       // 消息标题
  content             String      @db.Text               // 消息正文（最长 2000 字符）
  sender_id           BigInt?                            // 发送者 ID（null=系统）
  recipient_id        BigInt?                            // 接收者 ID（null=广播全体）
  related_resource    String?     @db.VarChar(50)        // 关联资源类型（survey/template/review）
  related_resource_id BigInt?                            // 关联资源 ID（可点击跳转）

  is_read             Boolean     @default(false)        // 是否已读
  read_at             DateTime?                          // 阅读时间

  created_at          DateTime    @default(now())
  updated_at          DateTime    @updatedAt
  deleted_at          DateTime?                          // 软删除时间

  // 关联关系
  sender              User?       @relation("SentMessages", fields: [sender_id], references: [id])
  recipient           User?       @relation("ReceivedMessages", fields: [recipient_id], references: [id])

  @@index([recipient_id, is_read, created_at])           // 用户收件箱查询（核心索引）
  @@index([type, created_at])                            // 按类型统计
  @@index([sender_id, created_at])                       // 管理员查看已发送
  @@index([deleted_at])                                  // 清理任务扫描
  @@index([created_at])                                  // 时间范围查询
}
```

### 3.2 User 模型追加关联

```prisma
model User {
```

### 3.3 表容量估算

```text
假设：
  • 日均活跃用户：500 人
  • 每用户日均收消息：3 条（通知+互动）
  • 管理员日均广播：1 条（500 用户 = 500 条写入）
  • 日均增量：500 × 3 + 500 = 2000 条

180 天数据量：
  • 2000 × 180 = 360,000 条
  • 单条平均 ~1KB → 总存储 ~360MB
  • PostgreSQL 单表 < 100 万行，性能无压力

索引大小：
  • 核心复合索引 (recipient_id, is_read, created_at) ≈ 15-20MB
```

### 3.4 索引设计说明

| 索引 | 用途 | 典型查询 |
|------|------|---------|
| `(recipient_id, is_read, created_at DESC)` | 用户收件箱（核心） | `WHERE recipient_id=$1 AND is_read=$2 ORDER BY created_at DESC LIMIT 20` |
| `(type, created_at)` | 管理员按类型统计 | `SELECT type, count(*) FROM messages WHERE created_at > $1 GROUP BY type` |
| `(sender_id, created_at)` | 管理员查看已发送 | `WHERE sender_id=$1 ORDER BY created_at DESC` |
| `(deleted_at)` | 定时清理任务 | `WHERE deleted_at IS NOT NULL AND deleted_at < $1` |
| `(created_at)` | 时间范围筛选 | `WHERE created_at BETWEEN $1 AND $2` |

```text
POST /api/messages/send

请求体：
{
  "content": "我有一个关于问卷发布的疑问...",
  "related_resource": "survey",        // 可选，关联资源类型

{
  "code": 429,
  "msg": "发送过于频繁，请稍后再试"
```

#### 4.2.7 管理员广播

```text
POST /api/admin/messages/broadcast

请求体：
{
  "title": "系统维护通知",
  "content": "平台将于 6月30日 凌晨 2:00-4:00 进行维护升级，届时部分功能可能暂时不可用。",
  "target_role": "all"                 // "all" | "super_admin" | "user"
}

校验规则：
  • title 必填，1-200 字符
  • content 必填，1-2000 字符
  • 广播频率限制：3 次/天/管理员
  • 消息 type 自动设为 admin_broadcast

实现说明：
  • 广播消息不逐条写入（避免 500 users × 1 broadcast = 500 INSERT），
    而是写入一条 recipient_id=NULL 的特殊记录，查询时通过
    "WHERE recipient_id = $myId OR (recipient_id IS NULL AND type = 'admin_broadcast')"
    来实现"所有人可见"。

响应 201：
{
  "code": 0,
  "msg": "广播已发送",
  "data": { "id": "44", "estimated_recipients": 486 }
}
```

| 状态码 | code | 说明 |

| 401 | 401 | 未认证 |
| 403 | 403 | 无权操作（非本人消息标记已读） |

## 五、权限与中间件

### 5.1 中间件层次

```text
请求进入
    │
    ▼
┌─────────────────┐
│ 1. authenticate  │  ← JWT 验证，提取 user_id + role
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 2. rate_limit    │  ← Redis 频率限制
│  send: 10/min    │     不同接口不同限制
│  broadcast: 3/day│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 3. authorize     │  ← 角色权限校验
│  • 读消息：仅本人 │     recipient_id == user_id
│  • 发消息：普通用户│     仅 user_admin_comm 类型
│  • 广播：super_admin│   仅 admin_broadcast 类型
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│ 4. sanitize      │  ← 内容安全
│  • XSS 过滤      │     HTML 标签转义
│  • 敏感词检测    │     敏感词库匹配
│  • 长度截断      │     content > 2000 → 截断
└────────┬────────┘
         │
         ▼
      业务逻辑
```

### 5.2 角色隔离实现

在 MessageService 中核心校验逻辑：

```text
sendMessage(sender, recipient, type, content):
  // 规则 1：禁止用户间通信
  if sender.role == "user" AND recipient.role == "user":
    throw ForbiddenError("不允许向其他用户发送私信")

  // 规则 2：普通用户只能发 user_admin_comm 类型
  if sender.role == "user" AND type != "user_admin_comm":
    throw ForbiddenError("普通用户只能发送咨询消息")

  // 规则 3：广播仅限管理员
  if type == "admin_broadcast" AND sender.role != "super_admin":
    throw ForbiddenError("仅管理员可发送广播")

  // 规则 4：系统通知仅由服务端内部触发
  if type in ("operation_notify", "template_like", "survey_lifecycle")
     AND caller_is_http_request:
    throw ForbiddenError("系统通知仅由服务端内部生成")
```

### 5.3 频率限制配置

| 接口 | 限制维度 | 阈值 | 时间窗口 |
|------|:---:|:---:|:---:|
| `POST /api/messages/send` | 按 user_id | 10 次 | 1 分钟 |
| `POST /api/admin/messages/broadcast` | 按 admin_id | 3 次 | 1 天 |
| `GET /api/messages` | 按 IP | 60 次 | 1 分钟 |
| `GET /api/messages/unread-count` | 按 user_id | 30 次 | 1 分钟 |

频率限制复用现有的 `checkRateLimit` 工具（Redis INCR + EXPIRE 模式）。

```text
                           │
              ┌────────────▼────────────┐
              │   MessageService         │
              │   .getUnreadCount(uid)   │
              └────────────┬────────────┘
                           │
              ┌────────────▼────────────┐
              │   Cache-Aside 模式       │
              │                          │
              │  Redis? ──YES──→ 返回    │
              │   │                      │
              │   NO                     │
              │   │                      │
              │   ▼                      │
              │  DB COUNT                │
              │  WHERE recipient_id=$uid │
              │    AND is_read=false     │
              │    AND deleted_at IS NULL│
              │   │                      │
              │   ▼                      │
              │  写入 Redis (TTL 1h)     │
              │  返回                    │
              └─────────────────────────┘
```

### 6.2 缓存键设计

| Redis Key | 类型 | 内容 | TTL |
|-----------|------|------|:---:|
| `msg:unread:{user_id}` | HASH | `{ total: "5", operation_notify: "2", ... }` | 1h |
| `msg:unread:total:{user_id}` | STRING | `"5"` | 1h |

选择 HASH 结构：单次 HGETALL 即可获取总数 + 各类型计数，一次 Redis 往返。

### 6.3 缓存失效策略

```text
触发场景                   →  操作
──────────────────────────────────────────────────
系统发送消息给用户          →  HDEL msg:unread:{uid}  (删除缓存，下次查询重建)
用户标记单条已读            →  HDEL msg:unread:{uid}
用户标记全部已读            →  HDEL msg:unread:{uid}
管理员发送广播（全体可见）   →  批量失效：
                                 SCAN msg:unread:* → DEL (异步，不阻塞主流程)
```

**广播失效优化**：广播的缓存失效不是逐用户 DEL，而是通过 **版本号** 机制：

```text
Redis Key: msg:broadcast:version    STRING  "42"  (最新广播 ID)

用户查询未读数时：
  1. 获取 DB 计数：自己的私信未读数
  2. 获取 msg:broadcast:version → 最后一条广播 ID
  3. 比对：用户上次已读的广播版本号（存 DB 或 Redis）
  4. 广播未读数 = 新广播数（version 差）
  5. 总数 = 私信未读 + 广播未读
```

此方案避免广播时遍历所有用户的缓存 key。

### 6.4 性能考量

| 操作 | 有缓存 | 无缓存 | 说明 |
|------|:---:|:---:|------|
| 查询未读数 | < 5ms (Redis) | 15-30ms (DB COUNT) | 高频操作，缓存收益大 |
| 消息列表首页 | — | 10-25ms (索引覆盖) | 不需要缓存（数据变化频繁） |
| 发送消息 | 失败时回退 | 20-40ms (INSERT + 索引更新) | 写入路径不做缓存 |

## 七、消息清理机制

### 7.1 清理策略

| 消息状态 | 保留期限 | 清理方式 | 理由 |
|---------|:---:|------|------|
| 已读 + 普通类型 | 180 天 | 定时任务物理删除 | 读过的通知无长期保留价值 |
| 已读 + 用户-管理员通信 | 365 天 | 定时任务物理删除 | 可能有纠纷追溯需求 |
| 未读消息 | 不限 | 不过期 | 必须用户主动读取 |
| 软删除消息 | 30 天 | 定时任务物理删除 | 回收站缓冲期 |
| 管理员广播 | 365 天 | 定时任务物理删除 | 公告类有存档价值 |

### 7.2 定时清理任务

```text
任务名: message-cleanup
调度方式: node-cron 内置于 q-server 进程（类似 log-consumer 模式）
         或在 q-server 中注册 Fastify setInterval

执行时间: 每日凌晨 03:00（业务低峰期）

清理 SQL（分批执行，每次 500 条，间隔 100ms）：
  -- 清理已读过期消息
  DELETE FROM messages
  WHERE is_read = true
    AND type IN ('operation_notify', 'template_like', 'survey_lifecycle')
    AND created_at < NOW() - INTERVAL '180 days'
  LIMIT 500;

  -- 清理已读通信消息
  DELETE FROM messages
  WHERE is_read = true
    AND type = 'user_admin_comm'
    AND created_at < NOW() - INTERVAL '365 days'
  LIMIT 500;

  -- 清理软删除过期消息
  DELETE FROM messages
  WHERE deleted_at IS NOT NULL
    AND deleted_at < NOW() - INTERVAL '30 days'
  LIMIT 500;

分批原因: 避免单次大 DELETE 锁表过久，每批 500 条 + 100ms 间隔
         让其他查询有充足的锁窗口。
```

### 7.3 清理日志与监控

每次清理完成后记录：

```text
{
  level: "info",
  msg: "消息清理任务完成",
  cleaned_read: 1234,
  cleaned_deleted: 56,
  elapsed_ms: 3200,
  timestamp: "2026-06-28T03:00:05.000Z"
}
```

异常时告警（P3 级别，每日报告汇总）。

## 九、实时性方案

### 9.1 方案选型

| 方案 | 实现复杂度 | 实时性 | 服务器开销 | 推荐 |
|------|:---:|:---:|:---:|:---:|
| **短轮询**（30s） | 低 | 延迟 ≤ 30s | 低（Redis 缓存命中 > 95%） | ✅ 推荐 |
| SSE 长连接 | 中 | 实时 | 中（N 个连接 × 内存） | 可选升级 |
| WebSocket | 高 | 实时 | 高 | 过度设计 |

**选择短轮询的理由**：
- 消息不是即时通讯（IM），30 秒延迟完全可接受
- 现有 Redis 缓存让轮询成本极低（< 5ms Redis HGETALL）
- 不增加连接管理复杂度
- 可与现有 SSE Client（`packages/sse-client/`）共用底层

### 9.2 升级路径（如需要实时推送）

如果未来需要实时推送，可以在 q-server 中新增 SSE 端点：

```text
GET /api/messages/stream
  → 订阅 Redis Pub/Sub channel "msg:user:{user_id}"
  → 新消息到达时 publish → 推送给对应 SSE 连接
  → 前端 EventSource 接收 → 更新未读计数 + 消息列表
```

## 十、安全考量

### 10.1 内容安全

| 层级 | 措施 |
|------|------|
| **前端输入** | 长度限制（maxlength="2000"），禁止 HTML 标签 |
| **API 层** | `content` 正则校验：`/^[一-龥a-zA-Z0-9\s\.,!?;:'"()（）【】《》、。，！？；：""''\-_@#$%^&*+=<>\/\[\]{}|~`]+$/` |
| **存储层** | 服务端对所有用户输入内容做 HTML 实体转义后再存储 |
| **展示层** | 前端渲染时使用 `v-text` / `{{ }}`（Vue 自动转义），不使用 `v-html` |

### 10.2 权限安全

| 风险 | 防护措施 |
|------|---------|
| 越权读取他人消息 | `recipient_id` 强制等于 `req.user.id`；管理员查看已发送消息通过 `sender_id` |
| 越权标记他人消息已读 | `PUT /messages/:id/read` 校验 `message.recipient_id === req.user.id` |
| 伪造系统通知 | 系统通知类型（operation_notify 等）只能由服务端内部调用，HTTP 接口拒绝 |
| 广播滥用 | 广播频率限制 3 次/天 + 审计日志记录每次广播操作 |

### 10.3 数据安全

| 措施 | 说明 |
|------|------|
| 消息内容加密 | 不加密（非敏感数据），但数据库连接走 TLS |
| 敏感信息过滤 | 消息内容扫描用户手机号/邮箱/身份证 → 自动替换为 `***` |
| 软删除 | 不提供物理删除接口给用户，仅软删除（deleted_at 标记） |
| 审计追踪 | 每条消息的创建/读取/删除操作写入 `audit_logs` |
