## 2. 前后端对接方案

### 2.1 数据传输格式

**统一响应结构 (ApiResponse<T>)：**

```json
{
  "code": 0,
  "msg": "ok",
  "data": { ... }
}
```

**状态码规范：**

| HTTP 状态码 | code 字段 | 含义 | 触发场景 |
|-------------|----------|------|---------|
| 200 | 0 | 成功 | 正常返回数据 |
| 400 | 400 | 请求参数错误 | Zod 校验失败、业务规则不满足 |
| 401 | 401 | 未认证 | Token 缺失或无效 |
| 403 | 403 | 无权限 | 非问卷所有者操作 |
| 404 | 404 | 资源不存在 | 问卷/答卷/文件未找到 |
| 409 | 409 | 冲突 | 重复操作（重复提交/重复发布） |
| 429 | 429 | 限流 | 超过速率限制 |
| 500 | 500 | 服务器错误 | 未被捕获的异常 |

### 2.2 接口调用方式

**认证接口（/api/auth/*）：**
- 客户端：`authClient` (baseURL="/api", timeout=15s, 无 Token)
- 用途：登录、注册、Token 刷新、密码重置

**业务接口（/api/surveys/*, /api/q-editor/* 等）：**
- 客户端：`serverClient` (baseURL="/api", timeout=15s, Bearer Token)
- 请求拦截器自动注入 `Authorization: Bearer <accessToken>`
- 响应拦截器自动处理 401 → Refresh Token → 重试；429 → 限流提示

**C 端接口（无需认证）：**
- `/api/surveys/:id/public` — 问卷公开详情
- `/api/surveys/:surveyId/token` — 获取提交凭证
- `/api/surveys/:surveyId/responses` — 提交答卷

### 2.3 前后端数据流转约定

| 约定项 | 规范 |
|--------|------|
| BigInt → string | 所有数据库 BigInt 字段在 JSON 中序列化为字符串 |
| 日期时间 | ISO 8601 格式（`2026-06-26T10:30:00.000Z`） |
| 枚举值 | 后端使用数字 (0/1/2)，前端 API 层保留数字 |
| 空值 | `null` 表示数据库 NULL，`undefined` 表示字段不存在 |
| 分页参数 | `{ page: number, page_size: number }` + 响应含 `{ total, page, page_size }` |

#### 5.2.1 问卷聚合统计概览

```
GET /api/admin/stats/overview
认证: 需要 (管理员)
```

**查询参数：** 无（或可选 `date_from` / `date_to`）

**响应示例：**
```json
{
  "code": 0,
  "data": {
    "total_surveys": 12,
    "published_surveys": 8,
    "total_responses": 48320,
    "avg_completion_rate": 78.4,
    "responses_today": 156,
    "responses_this_week": 1208,
    "trend_7_days": [
      { "date": "2026-06-20", "count": 89 },
      { "date": "2026-06-21", "count": 134 }
    ]
  }
}
```

**实现方式：**
- `total_surveys` / `published_surveys`：`prisma.survey.count({ where: { deleted_at: null, status: ... } })`
- `total_responses`：`prisma.response.count()`
- `responses_today`：`prisma.response.count({ where: { submitted_at: { gte: todayStart } } })`
- `trend_7_days`：`prisma.response.groupBy({ by: ['submitted_at'], _count: true })` 或原始 SQL `GROUP BY DATE(submitted_at)`

**实现方式（按题型分组计算）：**

| 题型 | 聚合方式 | SQL / Prisma 思路 |

| cascader | 按叶子节点分组 | value 存储最终选中值，直接 GROUP BY |

## 6. 问卷答案存储方案

### 6.1 存储架构

```
┌─────────────────────────────────────────────────────────────────┐
│  一次问卷提交产生的数据：                                          │
│                                                                  │
│  responses 表 (1 行)                                             │
│  ├── id: 答卷主键 (BigInt → string)                              │
│  ├── survey_id: 所属问卷                                         │
│  ├── anonymous_id: 匿名标识                                      │
│  ├── status: 1=已提交                                            │
│  └── submitted_at: 提交时间                                      │
│                                                                  │
│  answers 表 (N 行，N = 答题组件数量)                              │
│  ├── response_id → responses.id                                  │
│  ├── component_id → survey_components.id                         │
│  ├── value: 单值答案 (String, 可空)                               │
│  └── values: 多选答案 (Json, 可空, PostgreSQL jsonb)             │
│                                                                  │
│  survey_components 表 (题目元数据，发布时写入，不随提交变化)       │
│  ├── type: 题型 (single_select / multi_select / ...)             │
│  ├── config: 组件配置 JSON (含标题、选项、样式等)                  │
│  └── order_index: 排序序号                                       │
└─────────────────────────────────────────────────────────────────┘
```

### 6.2 各题型答案存储映射

| 题型 | Answer.value | Answer.values | 还原方式 |
|------|-------------|---------------|---------|
| single_select | `"0"` (选项索引) | null | `JSON.parse(config).options.status[index].status` |
| option_select | `"选项A"` (选项文本) | null | 直接读取 |
| multi_select | null | `["选项A","选项B"]` | 直接读取数组 |
| single_pic_select | `"图片标题1"` | null | 直接读取 |
| multi_pic_select | null | `["图片标题1","图片标题2"]` | 直接读取 |
| text_input | `"用户输入内容"` | null | 直接读取 |
| personal-info-* | `"用户信息"` | null | 直接读取 |
| date_time | `"2026-06-26T10:30:00.000Z"` | null | `new Date(value)` |
| rate_score | `"3.5"` | null | `parseFloat(value)` |
| slider | `"50"` | null | `parseInt(value)` |
| cascader | `"西湖"` (叶子节点) | `["浙江","杭州","西湖"]` | values 获取完整路径 |
| matrix_single | `'{"0":2,"1":0}'` (JSON string) | null | `JSON.parse(value)` → 行:列索引映射 |
| transfer | null | `["0","2","1"]` (排序后索引) | 需 JOIN config.transferItems |
| signature | `"https://minio/xxx.png"` | null | 直接渲染图片 |
| text_note | — (展示型，无答案) | — | 不出现在 answers 表中 |

### 6.3 存储策略

| 策略项 | 选择 | 理由 |
|--------|------|------|
| 答案与组件分离 | ✅ 使用 `component_id` 外键关联 | 组件配置独立演进，答案不可变 |
| 单值/多值分离 | ✅ `value` + `values` 双字段 | 单值索引友好，多值 JSON 灵活 |
| 选项值 vs 索引 | ⚠️ 当前不统一 | 短期：保持现状；中期迭代：统一为存储选项文本 + options 快照 |
| 矩阵答案序列化 | ✅ JSON string 存储 | 后续迭代考虑将 `value` 改为 `Json` 类型原生存储 |
| 签名文件 | ✅ MinIO + survey_files 追踪 | 级联删除、预签名 URL 访问控制 |
| 答案不可变性 | ✅ 提交后不修改 | 保障数据完整性 |

### 6.4 存储事务设计

```
begin transaction:
  1. INSERT INTO responses (...) → response.id
  2. INSERT INTO answers (response_id, component_id, value, values) × N → bulk createMany
  3. UPDATE surveys SET responses_count = responses_count + 1 → 计数缓存更新
commit

成功后：
  4. Redis: DEL survey:token:{surveyId}:{token} → 消费临时凭证
  5. Redis: SET survey:submit:{fingerprintHash}:{token} → 去重标记 (TTL 24h)
  6. Redis: DEL survey:stats:{surveyId}* → 清除统计缓存
  7. RabbitMQ: 发送审计日志消息 → 异步写入 MongoDB
```

## 7. 问卷结果整理机制

### 7.1 数据聚合策略

参考腾讯问卷的统计分析模式，按三层递进实现：

```
第 1 层：基础计数 — 每题各选项的选择人数和百分比
第 2 层：交叉分析 — 按人口属性/提交时段等维度交叉统计
第 3 层：智能分析 — 文本情感分析、异常检测、趋势预测
```

**本次实现聚焦第 1 层，预留第 2/3 层扩展点。**

### 7.2 核心聚合 SQL 模式

**单选题聚合（最高频）：**

```sql
SELECT a.value, COUNT(*) as count
FROM answers a
JOIN survey_components sc ON a.component_id = sc.id
WHERE sc.survey_id = :surveyId AND sc.type IN ('single_select', 'option_select')
  AND a.value IS NOT NULL
GROUP BY a.value
ORDER BY count DESC
```

结果再与 `sc.config` 中的 options 数组 JOIN（应用层完成），将索引还原为选项文本。

**多选题聚合（需展开 JSON 数组）：**

```sql
SELECT elem, COUNT(*) as count
FROM answers a
CROSS JOIN LATERAL jsonb_array_elements_text(a.values) AS elem
JOIN survey_components sc ON a.component_id = sc.id
WHERE sc.survey_id = :surveyId AND sc.type IN ('multi_select', 'multi_pic_select')
GROUP BY elem
ORDER BY count DESC
```

**评分题聚合：**

```sql
SELECT
  COUNT(*) as count,
  AVG(value::numeric) as average,
  MIN(value::numeric) as min,
  MAX(value::numeric) as max
FROM answers
WHERE component_id = :componentId AND value IS NOT NULL
```

### 7.3 去重机制

| 层级 | 机制 | 触发条件 |
|------|------|---------|
| 前端 | 浏览器指纹 SHA-256 哈希 | 每次页面加载时采集 |
| 传输 | 临时 token (UUID v4, TTL 30min) | 页面加载时从后端获取 |
| 后端 | `survey:submit:{fingerprintHash}:{token}` Redis SET NX | 提交时原子检查 |
| 降级 | IP + User-Agent 组合 | 指纹采集失败 / Redis 不可用时 |

**去重记录 TTL 为 24 小时**，同一天内同一设备 + 同一 token 不允许重复提交。刷新页面会获取新 token，旧 token 有 60 秒过渡期。

### 7.4 统计分析性能优化

| 策略 | 说明 |
|------|------|
| 缓存层 | `survey:stats:{surveyId}` 缓存统计结果，TTL 5min，提交新答卷时失效 |
| 物化视图 | 高频问卷可创建 PostgreSQL `MATERIALIZED VIEW` 预聚合答案分布 |
| 异步计算 | 大问卷（> 10万答卷）的复杂交叉分析通过消息队列异步计算 |
| 分页加载 | 带关键词搜索的原始数据查询使用游标分页 |
