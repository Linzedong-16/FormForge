# Feature Specification: q-editor 问卷引擎无缝迁移

**Feature Branch**: `012-q-editor-engine-migration`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "帮我完成对q-editor的无缝迁移"

## Background（背景说明）

`packages/survey-engine` 是从 `app/q-editor` 早期版本中抽取出的跨项目共享问卷渲染引擎，`app/frontend`
已完全消费该共享包渲染问卷（只读渲染场景）。但 `app/q-editor` 目前仍保留一份完整的本地重复实现
（`components/SurveyComs/*`、`stores/useEditor.ts`），且这份本地实现在抽取之后独立演进，新增了共享包
中不存在的能力：题型组件的"选项联动候选池"（依赖题未完成时的提示态）、编辑器 Store 中按 `client_key`
管理动态规则（生成、查询、更新、规则引用查找）。若直接让 `q-editor` 切换为依赖共享包，会立即丢失这些
已上线能力，属于功能倒退。"无缝迁移"要求：迁移前后，`q-editor` 编辑器的可见行为与既有能力必须完全一致
（对使用者透明），且迁移完成后不再存在与共享包重复的本地代码。

- Q: `q-editor` 既有基线的 4 项失败单测与 4 项既有 TS 错误（其中 `Signature.vue(72,64)` 的 `TS2345` 位于本次迁移必改文件内）应如何计入 SC-001 的"零功能回退"验收范围？ → A: `Signature.vue` 内的既有 TS 错误须随 FR-010 改造一并修复；其余 3 处既有缺陷（与本次迁移无关的 TS 错误及既有失败单测）明确排除在"零回退"范围外，仅要求"不比迁移前更差"。
- Q: FR-010 列出的 5 项高风险分歧点（Signature 上传数据格式、PicItem 响应体解析、SinglePicSelect 答案发射）在共享引擎缺乏组件级自动化测试的情况下，仅靠手动回归能否充分支撑 FR-006 的"可追溯、无歧义"要求？ → A: 例外处理——针对 FR-010 列出的 5 项分歧点，复用现有 Vitest 基础设施补充最小化组件级自动化测试；其余题型仍以手动回归为主，不视为"引入新的专门测试基础设施"。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 编辑器用户功能零回退迁移 (Priority: P1)

作为问卷编辑器（`q-editor`）的日常使用者，我在迁移完成后打开编辑器时，所有题型的渲染、编辑面板、
选项联动候选池提示、动态规则（跳转/显隐/联动）配置与撤销/重做行为都应与迁移前完全一致，我不会察觉到
底层代码来源发生了变化。

**Why this priority**: 这是"无缝迁移"的核心承诺——任何可感知的功能缺失或行为差异都会直接影响正在使用
编辑器创建、维护问卷的真实用户，是最高优先级、不可妥协的验收标准。

**Independent Test**: 在迁移前对编辑器全部题型（选择类 5 种、输入类 1 种、备注类 1 种、高级类 6 种、
矩阵类 1 种，共 14 种业务组件 + 计算字段伪题型）及动态规则配置面板逐一录制/记录当前行为基线；迁移后
按同一基线逐项回归比对，全部一致即通过，无需依赖其他用户故事即可独立验证。

**Acceptance Scenarios**:

1. **Given** 一份包含"选项联动"规则的题目（如单选题依赖另一题作答结果收窄候选池），**When** 迁移完成
   后在编辑器中预览该题目且依赖题未作答，**Then** 系统展示"需先完成依赖题"提示态，且候选池收窄逻辑与
   迁移前一致（答案下标不发生错位）。
2. **Given** 一份已保存、包含 `client_key` 与动态规则（跳转/显隐）配置的存量问卷，**When** 在迁移后的
   编辑器中打开该问卷，**Then** 所有题目的 `client_key` 与规则配置正确加载、可编辑、可正常保存发布。
3. **Given** 编辑器中新增一道题目并为其配置动态规则，**When** 迁移后执行"删除某道被其他规则引用的题目"
   操作，**Then** 系统仍能正确识别并提示所有引用该题目 `client_key` 的规则（规则引用查找能力不丢失）。
4. **Given** 编辑器处于任意编辑状态，**When** 执行撤销/重做操作，**Then** 状态回退/前进行为与迁移前
   完全一致。

---

### User Story 2 - 共享引擎成为单一事实来源 (Priority: P2)

作为负责维护问卷渲染/编辑能力的开发者，我希望 `q-editor` 与 `app/frontend` 不再各自维护一份重复的题型
组件与状态管理代码，迁移完成后对共享引擎的一次修改即可同时惠及两个消费方，不需要再在两处分别修改。

**Why this priority**: 这是迁移的长期价值所在，但相较于 P1（不能让现有用户功能受损）优先级较低——即使
本次迁移暂未完全清理干净所有重复代码，只要 P1 的零回退承诺成立，也仍可视为一次成功的阶段性交付。

**Independent Test**: 迁移完成后，任选一个共享引擎中的题型组件做一次可验证的小幅调整（如修改某个提示
文案的展示条件），无需在 `q-editor` 本地重复代码中再做对应修改，即可在两个消费方同时观察到效果变化。

**Acceptance Scenarios**:

1. **Given** 迁移已完成，**When** 在共享引擎包中修复一个题型渲染问题，**Then** 无需修改 `q-editor` 或
   `app/frontend` 任一方的本地代码，两者均能获得修复效果。
2. **Given** 迁移已完成，**When** 检查 `q-editor` 本地目录，**Then** 不再存在与共享引擎功能重复的题型
   渲染组件、编辑面板组件或编辑器状态管理实现。

---

### User Story 3 - 迁移风险可验证、可回退 (Priority: P3)

作为负责把控本次迁移质量的评审者/维护者，我希望在迁移落地前有明确的回归验证手段，并在迁移后发现问题
时能够快速定位是共享引擎的问题还是迁移过程引入的问题，从而降低"无缝"承诺翻车的风险。

**Why this priority**: 属于保障性诉求，服务于 P1/P2 的可信交付，但不直接产生新的用户可见能力，故优先级
最低。

**Independent Test**: 提供一份迁移前后行为对照的验证清单（覆盖 User Story 1 列出的全部场景），评审者
可依据该清单独立完成验收，无需理解迁移的具体代码实现细节。

**Acceptance Scenarios**:

1. **Given** 迁移已完成并提交评审，**When** 评审者按验证清单逐项核对，**Then** 清单中的每一项均可追溯
   到明确的通过/失败结论，不存在"无法判断"的模糊项。

---

### Edge Cases

- 存量问卷（发布于"选项联动"或"动态规则 client_key 管理"功能上线之前）缺少 `client_key` 或相关配置字
  段时，迁移后系统如何处理？（应保持现有的"惰性补齐、不产生破坏性变更"兼容策略，不应因迁移而改变此
  行为）
- 若共享引擎在补齐 `q-editor` 独有能力后，其变更同时影响了 `app/frontend` 的渲染表现（例如 `app/frontend`
  此前从未支持选项联动，补齐后是否会在 `app/frontend` 侧"意外生效"），如何界定影响范围与验证责任？
- 迁移过程中如果发现共享引擎与 `q-editor` 本地实现在某个题型上存在无法简单归并的行为差异（不仅是"多
  一个功能"，而是逻辑本身不同），应如何决策取舍？
- `q-editor` 以 qiankun 子应用形式集成到 `main-app` 运行，以及独立单页运行两种模式下，迁移后是否都需要
  验证一致？
- `q-editor` 当前基线存在与本次迁移无关的既有缺陷（4 项既有失败单测、以及 `TemplateMarket.vue`、
  `packages/sse-client/src/ai.ts` 中的既有 TS 类型错误），这些缺陷不在本次迁移的修复范围内，验收时不得
  将其误判为本次迁移引入的回退；唯有 `Signature.vue` 内的既有 `TS2345` 类型错误因与 FR-010 要求改造的
  MinIO 上传逻辑同处一文件，须随该项改造一并修复。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 迁移后，`q-editor` 中全部题型渲染组件（选择类、输入类、备注类、高级类、矩阵类及计算字段
  伪题型）的交互行为必须与迁移前完全一致，包括"选项联动候选池"及"依赖题未完成"提示态。
- **FR-002**: 迁移后，`q-editor` 的编辑器状态管理必须保留现有的按 `client_key` 管理动态规则的全部能力：
  生成/惰性补齐 `client_key`、按 `client_key` 查询与更新规则配置、规则引用查找（用于删除题目前的引用
  提示）。
- **FR-003**: 系统必须在切换 `q-editor` 的依赖之前，先将其独有的新增能力与行为差异（完整清单见 FR-010）
  补齐进共享引擎包，使共享引擎成为功能超集，不允许任一消费方在迁移过程中经历能力空窗期。
- **FR-004**: 迁移完成后，`q-editor` 本地代码中不得再保留与共享引擎功能重复的题型渲染组件、编辑面板
  组件或编辑器状态管理实现；`q-editor` 必须通过共享引擎包提供的导出能力实现相应功能。
- **FR-005**: 迁移完成后，共享引擎包的后续变更必须能够同时服务于 `q-editor` 与 `app/frontend` 两个消费
  方，不允许后续再产生"某一方独立新增能力却未回补共享引擎"的功能分叉。
- **FR-006**: 系统必须提供覆盖 User Story 1 全部验收场景的回归验证手段，用于确认迁移前后 `q-editor`
  行为对等，且该验证结论必须可追溯、无歧义；其中 FR-010 列出的 5 项高风险分歧点必须复用现有 Vitest
  基础设施补充组件级自动化测试用例，不得仅依赖手动回归。
- **FR-007**: 迁移过程必须保持 `q-editor` 作为 qiankun 子应用的既有集成契约（`bootstrap`/`mount`/
  `unmount`/`update` 生命周期、独立运行模式回退、路由基路径可配置）不被破坏，独立运行与集成运行两种
  模式均须验证通过。
- **FR-008**: 迁移必须保证存量问卷数据（已保存的 `client_key`、动态规则配置、题目状态）在迁移后可被
  正确加载、编辑、发布，缺少上述字段的更早期存量问卷必须继续维持"惰性补齐、零破坏性变更"的兼容行为。
- **FR-009**: 迁移过程中一旦发现共享引擎与 `q-editor` 本地实现之间存在无法通过"取两者能力并集"解决的
  行为分歧，系统必须能够明确记录该分歧点，交由人工决策取舍，而不能默默采用任一方行为掩盖差异。
- **FR-010**: 系统必须将以下已确认的 `q-editor` 独有能力/行为差异补齐进共享引擎包（该清单为当前已知的
  最小集合，实现阶段发现的新分歧点依据 FR-009 处理并追加，不得删减已列项）：
  - 选项联动候选池：依赖题未完成时的"需先完成依赖题"提示态、候选池收窄逻辑（保持答案下标不错位）。
  - `client_key` 动态规则管理：生成/惰性补齐 `client_key`、按 `client_key` 查询与更新规则、删除题目前的
    规则引用查找。
  - `Signature`（签名）题型的 MinIO 图片上传能力：异步上传流程、上传中状态提示、上传失败或缺少
    `surveyId` 时降级为 base64 内联存储、`getSurveyId` 注入取值方式。
  - `PicItem`（图片上传项）上传成功回调的响应体结构兼容处理：新旧上传接口返回结构差异（嵌套
    `data.file_url` 与扁平 `file_url`）必须统一兼容解析，不得因结构不一致导致图片链接解析失败。
  - `SinglePicSelect` 题型的答案变化事件发射：选项变化时必须向上层发射 `updateAnswer`，确保答案被正确
    记录。

### Key Entities

- **共享问卷引擎（Survey Engine）**：跨 `q-editor` 与 `app/frontend` 共享的问卷渲染与编辑能力集合，
  包含题型组件、编辑面板组件、编辑器状态存储（Store）与工具函数；迁移后应成为两个消费方问卷编辑/渲染
  能力的唯一实现来源。
- **q-editor 本地问卷编辑模块**：迁移前 `q-editor` 中与共享引擎功能重复的本地实现（题型组件、编辑面板、
  编辑器 Store），迁移完成后应被移除。
- **选项联动规则（Option Dependency Rule）**：题目候选池（可选答案集合）随其依赖题目的作答结果动态收
  窄或提示"需先完成依赖题"的规则。
- **动态规则配置（Question Logic Config）**：以题目 `client_key` 为索引的跳转、显隐、联动等规则集合，
  支持按题目稳定标识查询、更新及"删除题目前查找引用方"。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 迁移后，User Story 1 所列全部验收场景（选项联动提示态、存量问卷 `client_key`/规则加载、
  规则引用查找、撤销重做）在回归验证中 100% 通过，零功能回退（不含迁移前已存在、与本次迁移改动范围
  无关的既有缺陷；改动范围内的既有缺陷须随对应改造一并修复，其余既有缺陷仅要求"不比迁移前更差"，
  不计入零回退判定，具体范围见 Edge Cases）。
- **SC-002**: 迁移完成后，`q-editor` 本地不再存在与共享引擎重复的题型渲染组件、编辑面板组件或编辑器
  状态管理代码（重复实现数量为零）。
- **SC-003**: 迁移完成后，任选一次针对共享引擎的题型组件调整，均可在不修改 `q-editor` 本地代码的前提
  下于 `q-editor` 中生效，验证"单一修改点覆盖全部消费方"成立。
- **SC-004**: 迁移前后，使用至少 3 份存量问卷（分别覆盖"无 `client_key`"、"有 `client_key` 无规则"、
  "有 `client_key` 且含跳转/联动规则"三种历史状态）进行加载-编辑-发布全流程验证，均无数据兼容性异常。
- **SC-005**: 迁移完成后，`q-editor` 独立运行模式与作为 `main-app` 的 qiankun 子应用集成运行模式均可
  正常加载、编辑、保存问卷，两种模式各完成一次完整编辑流程验证。

## Assumptions

- "无缝迁移"的范围限定为 `app/q-editor` 及其与共享引擎重复的本地实现；`app/frontend` 当前已完成对共享
  引擎的迁移，本次不对其进行改动。若补齐共享引擎能力（如选项联动）导致 `app/frontend` 侧行为发生变化，
  视为一次需要单独确认和验证的连带影响，而非本次迁移的强制交付目标。
- 共享引擎包（`packages/survey-engine`）现有的架构与导出方式（组件注册表、Pinia Store、工具函数）足以
  容纳 `q-editor` 独有的编辑态能力，无需为此重新设计引擎整体架构。
- 迁移按"先补齐共享引擎能力 → 再切换 q-editor 依赖 → 最后清理本地重复代码"的顺序分阶段推进，允许在
  中间阶段短暂并存两份实现用于对照验证，但最终交付状态必须满足 FR-004（本地重复代码清零）。
- 迁移验证以现有项目测试基线（单元测试 + 手动回归）为准，不引入新的专门测试基础设施（如端到端/视觉
  回归平台）；覆盖率不得低于迁移前 `q-editor` 与共享引擎各自的既有基线。例外：FR-010 列出的 5 项高
  风险分歧点须复用现有 Vitest 基础设施补充针对性组件级自动化测试，该例外不视为引入新测试基础设施。
- 迁移不改变问卷数据的持久化格式（后端存储结构），仅涉及前端渲染与编辑逻辑的实现来源变化。
