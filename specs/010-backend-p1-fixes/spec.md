**Created**: 2026-08-08

**Status**: Draft

## User Scenarios & Testing _(mandatory)_

### User Story 1 - CSV 导出大数据集流式处理 (Priority: P1)

导出答卷数据时，数据量可能达到数万至数十万份答卷。当前系统在处理大规模导出请求时，将所有答卷数据和答案一次性加载到服务器内存中，导致内存持续增长直至耗尽（OOM），引发服务崩溃。运维人员需要一种无论数据量多大都能稳定完成导出的机制。

**Why this priority**: 内存溢出直接导致服务进程崩溃，影响所有在线用户，是生产环境中最严重的可靠性问题之一。即使中小规模问卷，当答卷量积累到一定程度后也会触发。

**Independent Test**: 可通过构造包含 5 万份以上答卷的问卷数据，发起 CSV 导出请求，验证服务内存使用量保持平稳（不随数据量线性增长）且导出文件内容完整。

**Acceptance Scenarios**:

1. **Given** 某问卷有 10 万份答卷，**When** 管理员发起 CSV 导出请求，**Then** 系统以流式方式逐批读取数据并输出，服务内存占用保持稳定（增长不超过 50MB），导出文件包含全部 10 万条记录且格式正确。
2. **Given** 导出过程中客户端断开连接（如关闭浏览器），**When** 连接中断，**Then** 服务端停止继续读取数据，释放相关资源，不影响其他请求。
3. **Given** 某问卷仅有 3 份答卷，**When** 管理员发起 CSV 导出，**Then** 导出功能正常返回完整 CSV 内容，与修复前行为一致。

### User Story 2 - RabbitMQ 连接自动恢复 (Priority: P1)

消息队列（RabbitMQ）承载着邮件发送和用户行为埋点等异步任务。当 RabbitMQ 服务重启或网络闪断时，当前系统不会自动重新建立连接，导致后续所有邮件通知和埋点数据静默丢失，直到运维人员手动重启整个应用服务。

**Why this priority**: 消息队列断连后的静默失败直接影响核心业务流程——用户收不到验证码邮件（无法注册/登录）、埋点数据缺失（影响数据分析）。运维人员可能在不知情的情况下持续丢失数据。

**Independent Test**: 可通过模拟 RabbitMQ 重启（Docker 容器重启），验证系统在 RabbitMQ 恢复后自动重建连接并恢复消息投递能力。

**Acceptance Scenarios**:

1. **Given** 系统正常运行且 RabbitMQ 连接正常，**When** RabbitMQ 服务重启，**Then** 系统检测到连接断开后自动尝试重连，RabbitMQ 恢复后连接重建成功，后续邮件和埋点消息正常投递。
2. **Given** RabbitMQ 持续不可用超过 5 分钟，**When** 连接多次重试失败，**Then** 系统记录错误日志并继续以合理间隔（指数退避）重试，不会因频繁重连耗尽资源或阻塞业务请求。
3. **Given** RabbitMQ 在系统启动时不可用，**When** 系统启动完成，**Then** 业务服务正常启动（不阻塞），系统在后台持续尝试连接 RabbitMQ，连接成功后恢复消息投递。
4. **Given** 连接恢复后，**When** 新消息投递到队列，**Then** 使用新建的 Channel 正确投递，不会因复用已失效的旧 Channel 导致消息丢失或报错。

### User Story 3 - Redis 离线队列策略修正 (Priority: P1)

当 Redis 不可用时，ioredis 客户端的离线队列会将所有待执行命令缓存在内存中。当前配置启用离线队列（`enableOfflineQueue: true`），与代码注释中"不启用离线队列"的设计意图矛盾。Redis 长时间不可用时，积压的命令持续占用内存，可能导致内存压力增大甚至 OOM。

**Why this priority**: 这是一个"按注释行事但代码却反着做"的配置错误。离线队列在 Redis 不可用期间无限制积压命令，内存风险随着不可用时长线性增长。项目其他模块的设计原则是"Redis 不可用时降级放行"，应保持一致。

**Independent Test**: 可通过在 Redis 不可用时发起请求，验证命令立即失败返回错误（而非进入离线队列排队），且系统业务正常降级运行。

**Acceptance Scenarios**:

1. **Given** Redis 服务不可用，**When** 业务代码调用 Redis 命令（如缓存读写），**Then** 命令立即返回错误而非进入离线队列等待，业务逻辑按降级路径继续执行（如跳过缓存直接查数据库）。
2. **Given** Redis 不可用持续 10 分钟，**When** 期间有大量业务请求，**Then** 服务内存中无积压的 Redis 命令，内存使用量保持正常水平。
3. **Given** Redis 从不可用恢复为可用，**When** 业务代码再次调用 Redis 命令，**Then** 命令正常执行，缓存功能恢复正常。

### User Story 4 - 答卷删除后统计缓存同步失效 (Priority: P1)

当用户删除一份答卷时，系统仅清除答卷详情的缓存，但问卷统计数据的缓存（`statsBySurvey`、`statsOverview`）未同步失效。这导致删除答卷后，统计页面仍然显示包含已删除答卷的过期数据，直到相关缓存自然过期——在此期间数据不一致，影响决策准确性。

**Why this priority**: 数据一致性是统计功能的基础要求。答卷提交时缓存被正确更新（`submitResponse` 会失效统计缓存），但删除时不对称——这违反了"写入即失效"的缓存一致性原则。问卷创建者基于过期统计数据做出的决策可能是错误的。

**Independent Test**: 可通过提交答卷 → 查看统计（确认数据正确） → 删除答卷 → 再次查看统计，验证统计数据反映了删除后的真实数据。

**Acceptance Scenarios**:

1. **Given** 某问卷有 10 份答卷，**When** 管理员删除其中 1 份答卷，**Then** 统计缓存被清除，再次查询统计数据时返回 9 份答卷的正确统计结果。
2. **Given** 某问卷的统计缓存已被清除，**When** 多个用户同时查询该问卷统计，**Then** 系统重建缓存（Cache-Aside 模式），所有用户看到一致的统计数据。
3. **Given** 答卷删除事务成功但缓存清除失败（如 Redis 暂时不可用），**When** 缓存清除出错，**Then** 删除操作本身不受影响（答卷已正确删除），缓存清除错误被记录日志，缓存将在 TTL 到期后自动过期。

### User Story 5 - 验证码邮件发送失败可观测 (Priority: P1)

用户请求发送验证码时，系统将验证码存入 Redis 后，通过 RabbitMQ 异步投递邮件发送任务。当 RabbitMQ 不可用时（`amqp` 为 falsy），邮件投递被静默跳过——用户收到"发送成功"的响应，验证码已存入 Redis，但邮件永远不会到达。当前代码对此情况没有任何日志记录，运维人员无法排查"用户为什么收不到验证码"的问题。

**Why this priority**: 静默失败是运维的噩梦——系统表面上一切正常（返回成功、验证码已存储），但用户实际收不到邮件。这类问题排查成本极高（需要运维人员登录服务器检查 RabbitMQ 状态）。至少需要一条告警日志来暴露此异常状态。

**Independent Test**: 可通过在 RabbitMQ 不可用的环境下调用发送验证码接口，验证系统返回适当的错误信息或记录明确的警告日志。

**Acceptance Scenarios**:

1. **Given** RabbitMQ 服务不可用（`amqp` 为 falsy），**When** 用户请求发送验证码，**Then** 系统记录一条 WARN 级别日志，明确说明"邮件未发送，RabbitMQ 不可用"，并包含目标邮箱的脱敏信息。
2. **Given** RabbitMQ 服务不可用，**When** 用户请求发送验证码，**Then** 系统在响应中告知用户邮件服务暂时不可用，而非返回"发送成功"的误导性消息。
3. **Given** RabbitMQ 服务正常，**When** 邮件成功投递到队列，**Then** 行为与修复前一致，用户正常收到验证码邮件。

### Edge Cases

- **US1 (CSV 导出)**: 导出过程中数据库连接中断时如何处理？——流式读取应捕获查询错误，返回已输出的部分数据并附带错误标记，或在响应头中标记导出不完整。
- **US1 (CSV 导出)**: 并发导出请求对同一问卷如何处理？——每个导出请求独立处理，互不干扰。不做请求合并或去重。
- **US2 (RabbitMQ 重连)**: 重连过程中，旧的 Channel 上还有未确认的消息怎么办？——旧 Channel 关闭时未确认消息丢失，由业务层容忍（邮件/埋点场景允许偶尔丢失，但不能持续丢失）。
- **US3 (Redis 离线队列)**: 改为 `enableOfflineQueue: false` 后，业务代码中已有的 Redis 调用是否需要修改错误处理？——需要确保所有 Redis 调用点都有 try/catch 或 `.catch()` 降级处理（当前项目中已有此模式）。
- **US4 (统计缓存失效)**: 答卷批量删除场景如何处理？——当前系统无批量删除接口，暂不涉及。若未来新增，需同步处理。
- **US5 (sendCode 可观测)**: 如果验证码已存入 Redis 但邮件未发送，用户使用该验证码时会怎样？——验证码本身仍然有效（可用于注册/登录），但用户无法获知验证码内容，形成"死验证码"。修复后系统将明确告知用户邮件服务不可用，不会产生死验证码。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系统 MUST 支持以流式方式导出 CSV 数据，数据库端使用游标分批读取，每次仅加载有限数量（如 1000 条）的答卷数据到内存。
- **FR-002**: 系统 MUST 在 CSV 导出过程中将数据逐批写入 HTTP 响应流，而非在内存中构建完整 CSV 字符串后再返回。
- **FR-003**: 系统 MUST 在客户端断开连接时停止继续读取数据库数据并释放相关资源。
- **FR-004**: 系统 MUST 监听 RabbitMQ 连接的 `close` 和 `error` 事件，在检测到连接断开时自动发起重连。
- **FR-005**: 系统 MUST 使用指数退避策略控制 RabbitMQ 重连间隔，避免频繁重连消耗资源。
- **FR-006**: 系统 MUST 在 RabbitMQ 重连成功后重建 Channel，确保后续消息使用有效 Channel 投递。
- **FR-007**: 系统 MUST 将 Redis 离线队列配置改为 `enableOfflineQueue: false`，使 Redis 不可用时命令立即失败而非排队。
- **FR-008**: 系统 MUST 在答卷删除操作完成后，除清除答卷详情缓存外，同步清除该问卷的统计数据缓存（`statsBySurvey` 和 `statsOverview`）。
- **FR-009**: 系统 MUST 在 RabbitMQ 不可用（`amqp` 为 falsy）时，记录 WARN 级别日志说明邮件未发送的原因，并包含脱敏后的目标邮箱。
- **FR-010**: 系统 MUST 在 RabbitMQ 不可用时向用户返回明确的错误信息（如"邮件服务暂时不可用，请稍后重试"），而非返回"发送成功"。

### Key Entities

- **CSV 导出会话**: 表示一次正在进行的 CSV 导出操作，包含数据库游标位置、已输出行数等状态，生命周期为单次 HTTP 请求。
- **RabbitMQ 连接状态**: 表示与 RabbitMQ 的连接状态（已连接 / 断开中 / 重连中），系统根据此状态决定消息投递行为。
- **统计缓存键**: 包括 `statsBySurvey:{surveyId}`（单问卷详细统计）和 `statsOverview`（全局统计概览），需在答卷增删时同步失效。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: CSV 导出 10 万份答卷时，服务端内存增量不超过 50MB（修复前：内存随数据量线性增长，10 万份答卷约占用 500MB+）。
- **SC-002**: CSV 导出过程中，首字节响应时间（TTFB）不超过 3 秒（修复前：需等待全部数据加载完成后才返回响应）。
- **SC-003**: RabbitMQ 重启后，系统在 30 秒内自动恢复连接并恢复消息投递能力（修复前：永久断开直到手动重启服务）。
- **SC-004**: Redis 不可用期间，服务内存使用量无异常增长（修复前：离线队列持续积压命令导致内存增长）。
- **SC-005**: 答卷删除后，统计数据的最大不一致窗口从缓存 TTL（当前最长 10 分钟）缩短至 0（立即失效）。
- **SC-006**: RabbitMQ 不可用时，管理员可在日志中搜索到明确的 WARN 级别告警，包含脱敏邮箱和失败原因（修复前：无任何日志）。

## Assumptions

- CSV 导出采用 HTTP 分块传输编码（chunked transfer encoding），无需前端配合即可实现流式下载。
- RabbitMQ 重连机制不以独立守护进程形式实现，而是作为 Fastify 插件内部的事件驱动逻辑。
- Redis 离线队列关闭后，现有业务代码中所有 Redis 调用点已具备降级处理能力（try/catch 或 `.catch()`），无需额外改造。
- 统计缓存失效策略保持 Cache-Aside 模式不变（删除时清除缓存，读取时重建），不引入 Write-Through 等新缓存策略。
- sendCode 在 RabbitMQ 不可用时的行为变更（从静默跳过改为返回错误）可能影响前端用户体验，但这是合理的——让用户知道"现在不能发验证码"比"发了但永远收不到"更好。
- RabbitMQ 重连期间积压的邮件和埋点消息允许丢失，优先保证连接恢复后的新消息可靠投递。
