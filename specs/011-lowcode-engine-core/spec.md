# Feature Specification: 低代码引擎核心解耦（纯 TS Schema + 组件工厂）

**Feature Branch**: `[011-lowcode-engine-core]`

**Created**: 2026-08-18

**Status**: Draft

**Input**: User description: "帮我实现这个低代码引擎，工厂函数目前仅支持Vue3即可"

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 去除组件引用耦合，核心引擎回归纯 JSON Schema (Priority: P1)

作为 `packages/survey-engine` 的维护者，我需要该包内部的问卷 Schema 只保存题型的字符串标识和配置，不保存组件的运行时引用；渲染时通过"组件工厂"按字符串标识查找并渲染出实际的 Vue3 组件。这样问卷数据可以直接被 JSON 序列化/反序列化，不再需要现有的"组件引用还原"补丁。本次改造范围限定在 `packages/survey-engine` 包内部及其现有消费方（`app/frontend` 的问卷预览页面），`app/q-editor` 的本地分叉实现暂不涉及。

**Why this priority**: 这是当前架构里耦合最深、代价最明显的一处（组件函数引用混入数据模型），也是后续多框架扩展与后续两个前端迁移接入的前提条件，必须先解决。

**Independent Test**: 用新引擎重新生成一份问卷 Schema 后，直接 `JSON.stringify` 再 `JSON.parse`，不经过任何"重新挂载组件引用"的步骤，即可在 `packages/survey-engine` 自身的渲染体系及其现有消费方（`app/frontend` 的问卷预览页面）中正常渲染出全部题型；`app/q-editor` 现有分叉实现不受影响、无需同步改动。

**Acceptance Scenarios**:

1. **Given** 一份包含全部现有题型的问卷 Schema（仅含字符串 name + config，不含组件引用），**When** 通过 Vue3 组件工厂渲染，**Then** 每个题目都以正确的 Vue 组件呈现，且现有依赖该渲染结果的功能（如 `app/frontend` 的问卷预览页面）表现与改造前一致。
2. **Given** 通过 `packages/survey-engine` 的 API 构造或修改问卷 Schema，**When** 将其序列化为 JSON 用于存储或传递给消费方，**Then** 得到的数据是纯 JSON（不含函数/组件引用），且重新反序列化后无需任何"还原组件引用"的额外处理即可正常渲染。
3. **Given** 已有的显示/隐藏、跳转、选项联动、计算字段规则配置，**When** 迁移到新引擎渲染的问卷上，**Then** 所有规则的求值结果与迁移前完全一致。

---

### User Story 2 - 核心引擎与渲染框架完全解耦，可独立测试 (Priority: P2)

作为架构维护者，我需要核心引擎（Schema 类型定义、Schema 校验、规则引擎）与具体渲染框架彻底解耦：核心包中不出现任何 Vue（或其他框架）的 import。Vue3 的组件工厂作为一个独立的"适配层"实现，调用核心包提供的注册接口完成组件登记与查找。这样未来要支持 React/Angular 时，只需新增一个对应的适配层，核心包代码不需要改动。

**Why this priority**: 是本次解耦的核心目标，验证"多框架工厂函数"这一诉求在架构上是否成立；但相较 User Story 1，其价值要在真正新增第二个框架适配时才会完全体现，因此优先级次之。

**Independent Test**: 在不安装 Vue 依赖的环境下（例如核心包自身的单元测试），仅使用测试替身（假的组件占位符）调用组件工厂注册接口，即可完成 Schema 校验和规则引擎求值的全部测试，无需引入任何前端框架。

**Acceptance Scenarios**:

1. **Given** 核心引擎包的源代码，**When** 检查其依赖声明与 import 语句，**Then** 不存在对 Vue（或其他任何前端框架）运行时包的直接依赖。
2. **Given** 一个最小化的组件工厂实现（可以是测试替身，也可以是真实的 Vue3 工厂），**When** 调用核心包的注册接口注册题型与组件的映射，**Then** 核心包能够正确返回该题型对应的组件引用，供渲染层使用。
3. **Given** 未来需要新增一种框架适配（如 React），**When** 按照核心包暴露的工厂接口新增一个适配层实现，**Then** 无需修改核心包内的 Schema 类型定义、Schema 校验逻辑或规则引擎代码。

---

### User Story 3 - 编排状态交还宿主项目管理 (Priority: P3)

作为使用该引擎的宿主项目（当前为 `app/frontend`，未来将扩展至 `app/q-editor`）的开发者，我需要核心引擎只提供无状态管理框架依赖的纯函数/类（如撤销/重做管理器），而不是像现在一样把编排状态（撤销/重做栈、脏标记、当前选中题目、分页状态、持久化同步状态）内置在 `packages/survey-engine` 自带的 Pinia store（`stores/useEditor.ts`）里。宿主项目继续使用自己选择的状态管理方案来持有和驱动这些状态，只是底层调用核心引擎暴露的纯逻辑。

**Why this priority**: 价值主要是长期可维护性和技术选型自由度；`app/frontend` 当前仅将 `packages/survey-engine` 用于只读预览场景，短期内不会带来立即可见的用户价值，因此优先级最低，可以在前两个故事稳定后再推进。

**Independent Test**: 将 `packages/survey-engine` 内置的 `useEditor.ts` 中的撤销/重做逻辑拆分为不依赖 Pinia 的独立管理器类，核心引擎包本身不再直接依赖 Pinia，且撤销/重做行为（包括历史层数上限）与改造前一致；现有消费方（`app/frontend`）若不需要该能力，可以不接入。

**Acceptance Scenarios**:

1. **Given** 核心引擎导出的撤销/重做管理器，**When** 在宿主项目的状态管理中调用该管理器执行"记录快照/撤销/重做"操作，**Then** 题目状态正确回退或前进，且历史记录层数上限行为与现有实现一致。
2. **Given** 核心引擎包的依赖声明，**When** 检查其 package.json，**Then** 不存在对任何状态管理库（Pinia/Vuex/Redux 等）的强制依赖。

---

### Edge Cases

- `packages/survey-engine` 内已经存在的旧格式问卷数据（题目对象中混有组件引用，需要靠现有的组件引用还原机制处理）如何在运行时被自动检测并兼容转换为新的纯 JSON Schema 格式，且不影响 `app/frontend` 预览页面已在使用的问卷数据？
- 当渲染层在组件工厂中查找不到某个题型对应的组件时（例如数据来自旧版本、题型标识拼写不一致、新题型尚未在当前版本注册），应如何降级处理，避免整页渲染失败？
- 现有规则引擎依赖 `client_key` 作为题目的稳定引用键，迁移到新 Schema 结构后，必须保证已发布问卷的 `SurveyComponent.logic` 规则配置不失效、不需要人工重新配置。
- `app/q-editor` 的本地分叉实现暂不迁移，但仍与 `packages/survey-engine` 共享 `src/logic/` 规则子模块；本次改造必须保证该共享子模块的对外接口不发生破坏性变化，避免影响 `app/q-editor` 现有功能。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: `packages/survey-engine` 内部承载 Schema 定义、Schema 校验与规则引擎的核心逻辑子模块必须以纯 TypeScript 实现，不得直接依赖或 import 任何前端框架（Vue、React、Angular 等）的运行时代码或框架专属类型；该包内的 Vue3 适配层代码可以依赖 Vue，但必须与核心逻辑子模块保持清晰的目录/模块边界。
- **FR-002**: 核心引擎必须定义完整的问卷 Schema 类型（题型标识、题目配置、规则配置），且 Schema 中不得包含任何框架特定的组件运行时引用，题目与组件的关联只能通过字符串标识表达。
- **FR-003**: 核心引擎必须提供统一的组件工厂注册与查找接口，允许按渲染框架分别注册"字符串标识 → 组件"的映射；本次实现范围内只需提供 Vue3 的工厂函数实现，接口设计上不得限定为仅支持单一框架。
- **FR-004**: 核心引擎必须完整保留现有规则子系统的能力（题目可见性/隐藏、跳转、选项级联依赖、派生计算字段），迁移后规则的求值结果不得与迁移前产生差异。
- **FR-005**: 核心引擎不得内置或依赖任何特定状态管理方案（如 Pinia、Vuex、Redux），编排状态（撤销/重做、脏标记、当前选中项、分页、持久化同步状态）的持有与驱动职责交由宿主项目的状态管理层完成；核心引擎仅需导出无状态管理框架依赖的撤销/重做管理器等纯逻辑供宿主调用。
- **FR-006**: 系统必须在加载/渲染现有问卷数据时，自动检测并兼容转换含组件引用或缺少新增字段的旧格式题目数据为新的纯 JSON Schema 结构，转换过程对调用方透明，不需要专门的批量数据迁移脚本或数据库结构变更，确保迁移前已产生的问卷数据可用、可继续正常展示与收集答卷。
- **FR-007**: Vue3 组件工厂适配层必须能够在 `packages/survey-engine` 现有 Vue 组件体系的全部消费场景中（当前为 `app/frontend` 的问卷预览页面），替换当前基于组件引用的动态渲染方式，且不产生功能回退；`app/q-editor` 的本地分叉实现不在本次改造范围内。
- **FR-008**: 当组件工厂按题型标识查找不到对应组件时，渲染层必须有明确的降级处理（如渲染占位提示、跳过该题并记录告警），不得导致整份问卷渲染失败或页面崩溃。
- **FR-009**: 规则引擎所依赖的题目稳定引用键（`client_key`）在新 Schema 结构下必须继续保持稳定语义，迁移前后同一题目的引用键不得发生变化。

### Key Entities _(include if feature involves data)_

- **LowCodeSchema（问卷 Schema）**: 纯 JSON 结构，描述一份问卷的题目列表，每个题目仅包含题型字符串标识、唯一 id、稳定引用键、配置对象与可选的规则配置，不包含任何组件运行时引用。
- **ComponentFactory（组件工厂）**: 按渲染框架实现的注册表，负责维护"题型标识 → 该框架下的组件"映射，并对外提供注册与查找能力；本次范围内的具体实现是 Vue3 工厂。
- **RuleEngine（规则引擎）**: 既有的可见性、跳转、选项联动、计算字段求值能力，本次改造中原样保留核心算法，仅随核心引擎一起下沉为不依赖渲染框架的纯逻辑模块。
- **OrchestrationState（编排状态）**: 撤销/重做历史、脏标记、当前选中题目、分页状态、持久化同步状态等，数据本身仍由宿主项目（当前为 `app/frontend`，未来扩展至 `app/q-editor`）的状态管理持有，但依赖核心逻辑子模块导出的无框架依赖的管理器类完成具体行为。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: `packages/survey-engine` 现有消费方（`app/frontend` 的问卷预览页面）在切换到新引擎后，人工验收全部现有题型的渲染与规则联动功能，均与改造前表现一致，无功能回归；`app/q-editor` 不受影响。
- **SC-002**: 新生成的问卷 Schema 可以被直接序列化为 JSON 再还原，无需任何额外的"组件引用还原"步骤，且还原后的渲染结果与序列化前一致。
- **SC-003**: 核心引擎包在不安装任何前端框架依赖的环境下，可以独立完成其自身的全部单元测试（Schema 校验、规则引擎求值），验证其与渲染框架无关。
- **SC-004**: 后续新增一种渲染框架适配（如 React）时，核心引擎包内的 Schema 类型定义、Schema 校验逻辑与规则引擎代码均无需修改，只需新增独立的适配层代码。
- **SC-005**: 已发布问卷在迁移前后，规则求值结果（可见性/跳转/联动/计算字段）100% 一致，不出现任何因数据结构迁移导致的规则失效。

## Assumptions

- 本次实现范围仅需要落地 Vue3 的组件工厂；React、Angular 等其他框架的工厂函数留待后续迭代，本次不实现，但接口设计需要为其预留扩展空间。
- 现有 `packages/survey-engine/src/logic` 目录下的规则引擎算法（可见性/跳转/选项联动/计算字段的求值与校验逻辑）保持不变，本次改造只是将其重新组织进解耦后的核心包，不改变算法本身。
- 本次改造范围明确限定在 `packages/survey-engine` 包内部及其现有消费方 `app/frontend`（问卷预览页面）；`app/q-editor` 的本地分叉实现暂不迁移，作为独立的后续迭代处理。后续计划依次推进 `app/frontend` 与 `app/q-editor` 两个前端接入解耦后的核心引擎，但具体迁移时间与顺序不在本次规格范围内。
- 旧格式问卷数据（题目对象中混有组件引用）到新纯 JSON Schema 格式的转换采用运行时自动兼容转换的方式常驻实现，不安排"下线兼容代码"的固定时间点；何时移除该兼容路径留待后续两个前端迁移全部完成后再评估。
- 核心引擎导出的撤销/重做管理器等编排相关纯逻辑，本次只需在 `packages/survey-engine` 包内完成拆分与导出，是否在 `app/frontend` 侧实际接入使用由该消费方自行决定，不强制要求。
